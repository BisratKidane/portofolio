## v1.1 Requirements — all complete

### Password Reset Hardening (RESET) — Fix #1

- [x] **RESET-01**: `requestPasswordReset` no longer returns the reset token; `PasswordResetPayload` dropped the `resetToken` field.
- [x] **RESET-02**: Reset token delivered to the account owner via the mailer with a `${CLIENT_URL}/reset-password?token=...` link.
- [x] **RESET-03**: Same generic message whether or not the account exists (anti-enumeration preserved).
- [x] **RESET-04**: Single-use + 30-min expiry preserved, proven by regression test.
- [x] **RESET-05**: `ForgotPassword` shows a static "check your email" state; no raw token rendered.
- [x] **RESET-06**: Reset token stored hashed at rest (`sha256`); lookup by hash. Delivered in Phase 9 (reopened the same `resetPassword` resolver).

### Mailer Abstraction (MAIL)

- [x] **MAIL-01**: Pluggable mailer with a single `sendMail({ to, subject, text/html })` — console driver in dev/test (no egress), SMTP-wired for prod without a rewrite.
- [x] **MAIL-02**: Tests assert "an email was sent" (recipient + token/link) at the mailer boundary without a live transport.

### JWT Secret Fail-Fast (SECRET) — Fix #2

- [x] **SECRET-01**: In production, an unset or `'change-me'` `JWT_SECRET` refuses boot (non-zero exit) before serving traffic.
- [x] **SECRET-02**: In development/test the existing fallback still applies — the fail-fast never crashes local dev or the suite.

### Rate Limiting (RATE) — Fix #3

- [x] **RATE-01**: `login` rate-limited per IP (5 / 15 min), rejected before credentials are checked.
- [x] **RATE-02**: `register` rate-limited per IP (5 / hour).
- [x] **RATE-03**: `requestPasswordReset` rate-limited per IP (5 / hour).
- [x] **RATE-04**: Enforced in a layer the in-process `executeOperation()` harness exercises, keyed by IP + parsed GraphQL operation (AST-based) so `me`/`dashboard` are unaffected.
- [x] **RATE-05**: A breach returns a generic "too many requests" error and does not leak account existence (429-count parity proven).

### Session Revocation (SESS) — Fix #4

- [x] **SESS-01**: `User` model gained a `passwordChangedAt` timestamp column.
- [x] **SESS-02**: `resetPassword` sets `passwordChangedAt = now()` on password change.
- [x] **SESS-03**: A JWT whose `iat` predates `passwordChangedAt` is treated as unauthenticated; second-vs-millisecond precision handled, same-second boundary proven.

### Password Strength (PWD) — Fix #5

- [x] **PWD-01**: `register` rejects passwords shorter than 8 chars server-side, before hashing.
- [x] **PWD-02**: `resetPassword` enforces the same 8-char minimum server-side.

### Email Verification (VERIFY) — Fix #6

- [x] **VERIFY-01**: `User` model gained `emailVerified` (bool, default false), `emailVerificationToken`, `emailVerificationExpiresAt`.
- [x] **VERIFY-02**: `register` creates an unverified user, sends a verification email, returns a message-only payload — no JWT/session/ADMIN at registration.
- [x] **VERIFY-03**: `verifyEmail(token)` flips `emailVerified`, clears the token (single-use), returns an `AuthPayload`.
- [x] **VERIFY-04**: ADMIN assigned at verification time to the first *verified* user only — race closed via atomic transaction + locking `FOR UPDATE` admin-count read + retry-once-on-deadlock, with a deterministic concurrency regression test (Plan 11-08).
- [x] **VERIFY-05**: `login` rejects an unverified account with a clear message after password validation.
- [x] **VERIFY-06**: Verification token is cryptographically random, single-use, 24h expiry.
- [x] **VERIFY-07**: `resendVerificationEmail(email)` reissues a fresh token/email for an unverified account.
- [x] **VERIFY-08**: `/verify-email` frontend route reads the token, calls `verifyEmail`, logs the user in; `Register` shows a "check your email" state; `AuthContext` handles the message-only register response without a session.

### CORS Hardening (CORS) — Fix #7

- [x] **CORS-01**: A rejected CORS origin is logged server-side; the client-facing error is generic (origin no longer echoed).

## Future Requirements (carried to v2)

- **RATE-F1**: Operation-aware graduated limits / a coarse IP-only `/graphql` guard as defense-in-depth.
- **VERIFY-F1**: Env-seeded initial admin (`ADMIN_EMAIL`) as belt-and-suspenders atop verification-gated role assignment.
- **UX-F1**: Frontend-specific friendly 429 message and a password-strength meter.

## Out of Scope (unchanged at close)

- Live email-provider account (SES/SendGrid/Postmark credentials) — deployment concern.
- Refresh-token rotation / server-side denylist / multi-device logout — `passwordChangedAt` is the chosen revocation mechanism.
- MFA / OAuth / social login — no new auth methods.
- CAPTCHA / bot detection — rate limiting is the chosen mitigation.
- Password composition rules/history/rotation — length-only minimum (NIST-aligned).
- Sequelize migrations — deferred to an infra-hardening milestone.
- GraphQL query depth/complexity limiting — separate pre-existing concern.
- UI redesign — frontend changes limited to what the security fixes required.
