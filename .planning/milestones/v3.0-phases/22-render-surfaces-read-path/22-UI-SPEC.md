# Phase 22 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope:** read-path only — VIEW-01 (`/family` tree card), VIEW-02 (`/manage` relationship panels + admin table), FIND-01 (admin-table Ge'ez search). No entry/edit UI (Phase 23). No new data, API, or helper logic — every surface consumes `getGeezDisplay(member)` from `frontend/src/utils/displayName.js` (Phase 21, locked, do not modify).

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing |
| md | 16px | Default element spacing |
| lg | 24px | Section padding |
| xl | 32px | Layout gaps |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing |

Exceptions: **Inherited, not introduced this phase.** `MemberNode.jsx`'s tree card already uses MUI spacing-unit shorthand that doesn't land on 4px multiples: `p: 0.75` (6px card padding), `gap: 0.25` (2px between stacked text rows), `gap: 1` (8px between the avatar column and the text column). These are pre-existing (Phase 17 / quick task 260726-sh4) and out of scope to change this phase — the new Ge'ez row reuses the same `gap: 0.25` rhythm so it doesn't introduce a new spacing value.

## Typography

Net-new typographic element this phase: the **Ge'ez secondary line**. It must use one identical size/weight/color treatment on all three surfaces (tree card, admin table, relationship-panel card) — do not vary per surface.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (Latin primary name) | 14px | 600 | 1.3 (`noWrap`, single line) |
| Label (Ge'ez secondary line — new) | 12px | 400 | 1.3 (`noWrap`, single line) |
| Heading (not touched this phase) | — | — | — |
| Display (not touched this phase) | — | — | — |

**Ge'ez line spec (all 3 surfaces, identical):**
- `fontSize: 12`, `fontWeight: 400`, `color: colors.slate` (= MUI `text.secondary`, matches `theme.js:45`)
- `lang="ti"` on the element (from the helper's payload — do not hardcode; read `geez.lang`)
- No `dir` attribute change — Ge'ez/Ethiopic is LTR
- `noWrap` + MUI's default text-overflow ellipsis (same as the existing Latin `fullname` treatment) — required because Ethiopic glyphs render visually wider than Latin at the same character count (STATE.md blocker)
- Rendered via the exact pattern from `21-RESEARCH.md`: `{geez && <Typography sx={{ fontSize: 12, fontWeight: 400, color: colors.slate }} lang={geez.lang} noWrap>{geez.text}</Typography>}` where `geez = getGeezDisplay(member)`

This reuses the tree card's existing `ROW_SX` token (`{ fontSize: 12, fontWeight: 400, color: colors.slate }`, `MemberNode.jsx:51`) verbatim for the Ge'ez row — no new token is created on the tree card. On `AdminMemberTable.jsx` and `MemberCard.jsx`, apply the same three values explicitly (those files don't currently have a `ROW_SX`-equivalent constant; inline `sx` with these exact values, or MUI `variant="caption"` + `color="text.secondary"` which resolves to the same 12px/400/slate visual result — planner's call, values must match).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `colors.bg` `#f5f6fb` | Page background |
| Secondary (30%) | `colors.paper` `#ffffff` | Tree card fill (tinted per-gender), table rows, MemberCard surface |
| Accent (10%) | `colors.primary` `#6366f1` | Existing accent usage only — viewer ring outline, focus-root glow, "Head" tag chip/badge, linked-account icon (`LinkRoundedIcon`). **Not introduced or changed this phase.** |
| Destructive | `colors.error` `#ef4444` | Existing "Remove" button (`MemberCard.jsx:134`) — unaffected by this phase, no new destructive actions added |

Accent reserved for: viewer-ring outline, focus-root card glow/badge, "Head" tag, linked-account link icon. **Explicitly excluded: the Ge'ez name line.** Ge'ez text is secondary/muted information (`colors.slate`), never accent-colored — accenting it would visually imply it's an interactive or primary element, which contradicts D-02 ("Ge'ez line is visually secondary to the Latin primary").

## Component Contract (Phase-Specific)

### 1. `/family` tree card — `MemberNode.jsx` (VIEW-01)

**Layout mechanism (fixed 252×120px card, must not grow or vary):**
- The reserved top row (`MemberNode.jsx:167`, currently always `height: 18` regardless of content) becomes conditional: `height: isFocusRoot ? 18 : 0`. Today only the single re-rooted "Head" card ever renders content in that row; collapsing it to `0` on every other card reclaims ~18px of vertical budget for the new Ge'ez line *without* changing the outer `Paper`'s fixed `height: 120` — the outer card dimensions are untouched, only the inner content column's available space changes. This is the "absorb into the reserved-row budget" mechanism referenced by D-01.
- Insert the Ge'ez `Typography` immediately after the Latin `fullname` `Typography` (`MemberNode.jsx:189-191`), before the `birthday` row, using the `ROW_SX` token (see Typography section above).
- **Worst-case row count** (Head tag + Latin fullname + Ge'ez + birthday + mother + address, all present on the single focus-root card): still fits inside the fixed height via `noWrap`/ellipsis on every row (existing behavior); do **not** overflow, do **not** grow the card, do **not** drop a row to make room. This exact scenario is called out in `STATE.md`/CONTEXT as the mandatory manual visual check.
- When `getGeezDisplay(member)` is `null`: no extra row renders, card layout is byte-for-byte unchanged from today (L-04).

### 2. `/manage` admin member table — `AdminMemberTable.jsx` (VIEW-02, FIND-01)

- Name cell (`AdminMemberTable.jsx:111-114`): Ge'ez line stacked directly below the existing Latin `fullname` `Typography`, **inside the same `TableCell`** — no new column.
- Search filter (`AdminMemberTable.jsx:56-58`): extend `member.fullname.toLowerCase().includes(term)` to `member.fullname.toLowerCase().includes(term) || member.geezFullname?.toLowerCase().includes(term)` (guard `geezFullname` for `null` before calling `.includes`). `.toLowerCase()` on the Ge'ez side is a harmless no-op (Ethiopic has no case) — kept for code symmetry, not because it does anything.
- Only `fullname` OR `geezFullname` are matched — `geezFirstname`/`geezLastname` (redundant with `geezFullname`) and `geezMothersname` (not displayed in this cell) are explicitly excluded from the search per D-04.

### 3. `/manage` relationship-panel card — `MemberCard.jsx` (VIEW-02)

- Ge'ez line stacked directly below the existing Latin `fullname` `Typography` (`MemberCard.jsx:108-110`), inside the same `Box`/`Stack` — no restructuring, no new card region.

### 4. Query selection sets (SC4 — data prerequisite, not a visual change)

Each surface only renders if its GraphQL selection set includes the field. Add `geezFullname` to:
- `FAMILY_TREE_QUERY` (`FamilyTreePage.jsx:20`) — feeds the tree card
- `EDITABLE_MEMBER_FIELDS` + `FAMILY_MEMBERS_QUERY` (`ManagePage.jsx:28,43`) — feed the relationship panels, admin table, and its search

No raw `geezFirstname`/`geezLastname`/`geezMothersname` parts are needed by any surface this phase — all three consumers render/search `geezFullname` only.

### 5. Manual sign-off gate (cannot be automated)

jsdom cannot rasterize glyphs. Before phase close, a human must visually verify, on the actual `/family` tree, the **longest real Ge'ez name in the production dataset** rendered on a card that also has birthday + mother + address populated — confirming truncation/ellipsis behaves correctly and the card never overflows its fixed 120px height.
