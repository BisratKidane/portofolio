<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `editMember`'s target-selection vs. field-lock rule | A member-user chooses which in-scope member to edit; the server must still block edits to a relative who manages their own linked profile |
| `deleteMember` vs. any non-admin caller | The entire delete capability must not exist for a member-user, not merely reject after a check |
| `myEditableMembers` vs. client-supplied filters | The query accepts no arguments — the returned set is entirely server-derived from `user.familyMemberId`, never client-influenced |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-01 | Elevation of Privilege | `editMember` | mitigate | Non-admin scope check via `computeEditableScope`, identical pattern to every prior mutation in this phase |
| T-14-03 | Elevation of Privilege (field overwrite of self-managing member) | `editMember`'s D-06 field-lock | mitigate | `target.linkedUser.id !== user.id` check compares actual user identity, not just presence of a link; self-edit remains allowed via the identity match |
| T-14-04 | Elevation of Privilege (unauthorized delete) | `deleteMember` | mitigate | `requireAdmin(user)` is the resolver's only guard, with no `computeEditableScope` call anywhere in the function — members have zero delete capability by construction |
| T-14-10 | Information Disclosure | `myEditableMembers` | accept | Returns only the caller's own server-computed scope; no arguments exist for a client to request another user's scope, so no cross-user leak is possible by construction |

</threat_model>
