Ship the first two member-facing relationship mutations — `addParent` and `addSpouse` — each
always creating a brand-new `FamilyMember` node and linking it via the existing, reused Phase 12
service helpers (`linkParent`, `setSpouse`), gated by `requireFamilyAccess` and the

anti-escalation mutation surface; `addChild`/`addSibling` (which carry the primary SC-4 adversarial
test target, `otherParentId`) follow in 14-05.

mutation in this phase reuses, and extend `linkParent`/`setSpouse` to accept an optional
transaction so multi-step "create node + link it" writes are atomic (mirroring `linkUserToMember`'s
established transaction pattern from Phase 13).

transaction support.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Member-user-supplied `memberId`/`role`/`newMember` mutation args vs. server-computed scope | Client chooses which existing member to attach a new relative to; server must never trust a client-asserted scope |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-01 | Elevation of Privilege | `addParent`/`addSpouse` resolvers | mitigate | Every non-admin call checks `scope.ids.has(targetId)` (from `computeEditableScope`, 14-02) before any write; D-01 is enforced structurally — both mutations only ever accept a `newMember` payload for the relative being added, never an existing-node id for that relative |
| T-14-02 | Elevation of Privilege (re-parenting) | `addParent` | mitigate | Non-admins are rejected if the target's `motherId`/`fatherId` slot is already filled (D-05 add-only); only an ADMIN may overwrite an existing slot |
| T-14-SC | Tampering (data integrity) | Multi-step "create node + link" transactional writes | mitigate | Both mutations wrap the create-then-link sequence in `models.User.sequelize.transaction(...)`, mirroring the WR-01-fixed `linkUserToMember` precedent; a rollback test proves no orphaned `FamilyMember` row survives a mid-transaction failure |

</threat_model>
