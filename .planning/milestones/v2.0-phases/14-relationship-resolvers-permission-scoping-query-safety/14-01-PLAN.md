<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client GraphQL query -> Apollo Server validation phase | Untrusted, client-controlled query AST (shape/depth is attacker-influenced even for an authenticated caller) |
| Per-request context construction -> resolver execution | DataLoader instances must not outlive or cross the single request they were built for |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-06 | Denial of Service | Apollo Server `validationRules` | mitigate | `maxDepthRule({ n: env.maxQueryDepth, ignoreIntrospection: false })` registered in the shared `serverConfig.js`, consumed by both `server.js` and `test/helpers.js`; rejects before any resolver runs (0 DB cost); `MAX_QUERY_DEPTH` is a named, env-overridable constant per D-08 |
| T-14-07 | Denial of Service | `familyMember.loaders.js` | mitigate | Request-scoped DataLoader batching built here; full N+1 proof against real recursive schema fields lands in 14-03, but the batching mechanism itself is unit-tested in this plan |
| T-14-08 | Information Disclosure / Tampering | `createLoaders(models)` lifecycle | mitigate | Loaders constructed fresh per call (never module-level); Task 2's Test 5 directly proves two `createLoaders` calls do not share cache state |
| T-14-SC | Tampering (supply chain) | `dataloader`, `@escape.tech/graphql-armor-max-depth` npm installs | accept | RESEARCH.md's Package Legitimacy Audit performed this session — both `[OK]`, no `[ASSUMED]`/`[SUS]` flags; versions pinned to the verified `^2.2.3`/`^2.4.2` |
