Add the REL-06 sibling/child duplicate-name guard to `familyMember.service.js`'s `addChild`
function — the single write path both the `addChild` and `addSibling` resolvers already route
through — so every caller (member add, admin add, future callers) is covered by one function,

composition over Phase 14's shipped mutation surface). It is a data-integrity invariant spanning
two nullable FK columns with OR semantics, with no existing DB-constraint precedent in this
codebase — it must be built test-first, including a genuinely concurrent test, not a sequential
one (Pitfall 1 in 15-RESEARCH.md explicitly warns a sequential two-call test would pass even with
a naive, still-racy implementation).
Output: `addChild`'s REL-06 guard (row-locked, applies to every caller), `familyMember.dedup.test.js`,

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `addChild`'s `attrs.motherId`/`attrs.fatherId`/`attrs.firstname` (already-validated resolver output) → the service-layer write | The candidate child's parent FKs and firstname are the guard's only inputs; both `addChild` and `addSibling` resolvers construct `attrs` before this boundary, so the guard is the single, unconditional last-line-of-defense for the "no duplicate-named sibling" invariant regardless of caller |
| Two concurrent requests targeting the same shared-parent row | MySQL's default REPEATABLE READ isolation permits both to see "no duplicate" absent an explicit lock — the row lock IS the trust boundary enforcement mechanism |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-01 | Tampering (data-integrity TOCTOU) | `addChild`'s REL-06 guard | mitigate | `SELECT ... FOR UPDATE` (Sequelize `lock: t.LOCK.UPDATE`) on the shared-parent `FamilyMember` row(s), taken BEFORE the duplicate-name read, inside the same transaction as the eventual `FamilyMember.create` — serializes all concurrent `addChild`/`addSibling` calls targeting the same parent onto one connection at a time; proven by a genuinely concurrent `Promise.allSettled` test, not a sequential one (Pitfall 1) |
| T-15-02 | Elevation of Privilege (admin bypass) | `addChild`'s REL-06 guard | mitigate | The guard takes no `isAdmin`/role parameter and is placed unconditionally inside `addChild` itself — proven by an adversarial test where an ADMIN's duplicate-name `addChild` call is also rejected (Pitfall 4) |
| T-15-03 | Information Disclosure (error copy names a member) | REL-06 error message | accept | The message names the conflicting child and shared parent's fullname — both are already within the same declared-parent subtree the caller supplied (`attrs.motherId`/`attrs.fatherId`), which the caller must already know to have submitted the mutation; no cross-scope member is ever named that the caller didn't already reference themselves. Scope enforcement (who may act on `memberId` at all) is a separate, already-shipped Phase 14 check that runs BEFORE this guard is reached. |
