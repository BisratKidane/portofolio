# Milestone v1.1: Security Remediation

**Status:** ✅ SHIPPED 2026-07-21
**Phases:** 7–11
**Total Plans:** 19 (42 tasks)

## Overview

Remediated all seven security bugs that v1.0 deliberately documented but left unfixed — closing the account-takeover, brute-force, stale-session, and privilege-escalation vectors — while keeping the CI-enforced test suite green throughout. Every fix was delivered TDD red-green-refactor; v1.0 tests that documented a bug were flipped to assert the secure behavior as the red step. Dependency-first sequencing let each shared resolver (`resetPassword`, `login`, `register`, `verifyEmail`) be touched once rather than repeatedly.

## Phases

### Phase 7: Foundation Hardening — CORS, JWT Fail-Fast & Password Strength

**Goal**: The app refuses insecure configurations and weak passwords before they can cause harm, without ever crashing dev/test — and a new HTTP-level test harness exists for the Express-layer concerns the in-process GraphQL test helper can't reach.
**Depends on**: Nothing (first phase of v1.1; builds on the v1.0 test suite/harness)
**Requirements**: CORS-01, SECRET-01, SECRET-02, PWD-01, PWD-02
**Plans**: 2 plans

Plans:
- [x] 07-01: HTTP test harness (importable app + supertest) and CORS-01 origin-echo fix
- [x] 07-02: JWT-secret production fail-fast (SECRET-01/02) and 8-char password minimum (PWD-01/02)

**Success criteria met:** Rejected CORS origins never appear in client-facing errors (only server logs); production boot refuses an unset/`change-me` `JWT_SECRET`; dev/test boot normally on the weak shared secret; `register` and `resetPassword` enforce an 8-char minimum server-side.

### Phase 8: Mailer Abstraction & Reset-Token Remediation

**Goal**: Password reset tokens are never exposed via the API — they reach only the account owner, via a pluggable mailer — closing the documented account-takeover vector.
**Depends on**: Phase 7 (reuses the harness/TDD rhythm; otherwise independent)
**Requirements**: MAIL-01, MAIL-02, RESET-01, RESET-02, RESET-03, RESET-04, RESET-05
**Plans**: 3 plans

Plans:
- [x] 08-01: Mailer service (nodemailer, jsonTransport) + production SMTP boot assertion
- [x] 08-02: Frontend ForgotPassword confirmation panel + ResetPassword URL-token read
- [x] 08-03: Reset-token remediation — schema deletion + resolver mailer wiring + single-use/expiry regression tests

**Success criteria met:** `sendMail()` logs to console with zero network egress and is assertable at the boundary; `PasswordResetPayload.resetToken` removed at the schema level; the mailer receives the exact persisted token, only for real accounts; generic anti-enumeration message and single-use/30-min expiry preserved; `ForgotPassword` shows a static "check your email" state.

### Phase 9: Session Revocation via passwordChangedAt

**Goal**: Resetting a password immediately invalidates any JWT issued before the reset, closing the stale-session window.
**Depends on**: Phase 8 (touches the same `resetPassword` resolver — sequenced immediately after so that resolver is modified once)
**Requirements**: SESS-01, SESS-02, SESS-03, RESET-06
**Plans**: 3 plans

Plans:
- [x] 09-01: User model `passwordChangedAt` column + `beforeUpdate` hook stamp (SESS-01/02) + manual `ALTER TABLE` migration and human boot-verify (SC-4)
- [x] 09-02: Reset tokens hashed at rest across both resolvers (RESET-06, closes 08-REVIEW WR-08)
- [x] 09-03: `getUserFromRequest` revocation check + mandatory same-second boundary test (SESS-03)

**Success criteria met:** `passwordChangedAt` (millisecond precision, nullable, no backfill) set only inside the `changed('passwordHash')` hook branch; a JWT whose `iat` predates it is treated as unauthenticated (null-safe seconds-floor compare, same-second boundary proven); reset tokens stored as `sha256(token)`; SC-4 manually verified against a real pre-existing dev DB.

### Phase 10: Rate Limiting on Auth Mutations

**Goal**: Brute-force, enumeration, and reset-token-guessing attempts against `login`, `register`, and `requestPasswordReset` are throttled per client IP, without affecting normal app usage.
**Depends on**: Phase 8, Phase 9 (built after the auth resolvers reached final v1.1 shape)
**Requirements**: RATE-01, RATE-02, RATE-03, RATE-04, RATE-05
**Plans**: 3 plans

Plans:
- [x] 10-01: Rate-limit config map + TDD'd in-memory fixed-window store (RATE-04 foundation)
- [x] 10-02: TDD'd enforceRateLimit + Apollo plugin (AST-based field extraction) + server.js trust-proxy/clientIp/plugin wiring (RATE-01/02/03/04/05)
- [x] 10-03: test/helpers.js plugin wiring + global test isolation + mandatory RATE-01..05 proof suite (parity + bypass-resistance)

**Success criteria met:** `login` throttled (5/15min), `register`/`requestPasswordReset` (5/hour); implemented as an Apollo plugin keyed off the parsed operation AST (not the client-supplied `operationName`, closing a rename bypass), exercised by the in-process `executeOperation()` harness; ordinary `me`/`dashboard` queries unaffected; 429 count identical for real vs nonexistent accounts (no enumeration oracle); `trust proxy = 1`.

**Requirements**: VERIFY-01 … VERIFY-08

Plans:

- [x] 11-02: Mailer sendVerificationEmail + GraphQL schema contracts + resendVerificationEmail rate limit (VERIFY-02/03/07 groundwork)
- [x] 11-06: AuthContext message-only register + verifyEmail action (VERIFY-08 contract)
- [x] 11-03: Manual migration SQL + README documentation (VERIFY-01 / SC-5 groundwork)
- [x] 11-04: register creates an unverified user + login rejects unverified accounts (VERIFY-02/05/06)
- [x] 11-05: verifyEmail (race-safe ADMIN assignment) + resendVerificationEmail (VERIFY-03/04/06/07)
- [x] 11-07: Register confirmation state + /verify-email route + manual migration boot-and-verify (VERIFY-08 / SC-5) — SC-5 human sign-off 2026-07-21

FOR UPDATE` + retry-once-on-deadlock (11-08 gap closure); `login` rejects unverified accounts server-side; `resendVerificationEmail` recovers lost tokens; `/verify-email` route logs the user in on success; SC-5 manual boot-and-verify signed off against a real pre-existing dev DB.

## Milestone Summary

**Decimal/inserted phases:** None. Phase 11 carried one post-verification gap-closure plan (11-08) after the phase verifier flagged VERIFY-04's ADMIN promotion as non-atomic under real MySQL concurrency.

**Key Decisions:**
- Remediate all 7 documented security issues in one milestone (not just the flagship reset-token bug) — v1.0's suite made wholesale auth changes safe, and fixing them together avoided re-touching the same resolvers repeatedly. ✓ Good.
- One pluggable mailer (console driver in dev/test, SMTP-wired in prod) backs both password reset and email verification. ✓ Good.
- Every fix TDD'd red-green-refactor; v1.0 tests documenting bugs flipped to assert secure behavior; CI green throughout. ✓ Good.
- Dependency-first phase sequencing (7 foundation → 8 mailer → 9 passwordChangedAt on the same resolver → 10 rate limiting after resolvers stabilized → 11 verification last, largest blast radius). ✓ Good.
- Rate limiting keyed off the parsed GraphQL operation AST, not the client `operationName` string — closed an operation-rename bypass. ✓ Good.
- Phase 11 CR-01 Option B: verify+promote made atomic via one transaction + `FOR UPDATE` + retry-once-on-deadlock, chosen over statement-level timing. ✓ Good.

**Issues Resolved:**
- Reset-token API exposure (account-takeover) — token now mailer-delivered and dropped from the API; hashed at rest.
- Insecure default JWT secret — production fail-fast at boot.
- No auth-mutation rate limiting — per-IP fixed-window limits on login/register/requestPasswordReset.
- No session revocation — `passwordChangedAt` invalidates pre-reset JWTs.
- Weak passwords accepted — 8-char server-side minimum.
- First-user-becomes-ADMIN land-grab race — DB-enforced atomic verify+promote.
- CORS rejection echoing the rejected origin — now generic client-facing error, origin only in server logs.

**Technical Debt / Deferred:**
- Live email-provider account (SES/SendGrid/Postmark) — mailer is provider-ready; standing up an account is a deployment concern (deferred).
- Sequelize migrations vs `sync()` — new columns added via the model-field pattern; migration tooling deferred to an infra milestone. Phases 9 & 11 required manual `ALTER TABLE` + human boot-verify because `sync()` won't alter existing tables.
- RATE-F1 (operation-aware graduated limits / coarse `/graphql` guard), VERIFY-F1 (env-seeded initial admin), UX-F1 (429 UX + password-strength meter) — deferred to v2.
