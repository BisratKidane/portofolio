<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `deleteMember` transaction boundary | The only mutation path in this phase capable of permanently destroying `FamilyMember`/`Spouse` rows — a bug here is a real, unrecoverable data-loss risk for blood relatives once real family data is entered (Phase 15+). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-12-11 | Data Destruction / Tampering | `deleteMember` married-in check | mitigate | `isMarriedInOnly` is evaluated for every partner using pre-delete graph state, strictly BEFORE any `destroy()` call executes in the same transaction — proven by the blood-survival test (a spouse with a parent link always survives). |
| T-12-12 | Data Destruction | `deleteMember` recursion depth | mitigate | The married-in check is computed ONLY for the direct partner(s) of the target being deleted — never recursively re-evaluated for a removed partner's own spouses; proven by the two-hop non-recursion test. |
| T-12-13 | Tampering | `setSpouse` concurrent-write race (TOCTOU on canonical ordering) | mitigate | `sequelize.transaction()` wraps the create attempt, and a caught `SequelizeUniqueConstraintError` is treated as idempotent success rather than a hard failure, backed by the real DB-level unique index from Plan 12-02 as the actual source of truth. |
| T-12-14 | Repudiation | Partial-failure mid-delete (e.g. process crash between `Spouse.destroy` and `FamilyMember.destroy`) | mitigate | The entire operation runs inside one `sequelize.transaction()` — MySQL rolls back all statements atomically on any failure, so no partial/orphaned state is possible. |
</threat_model>
