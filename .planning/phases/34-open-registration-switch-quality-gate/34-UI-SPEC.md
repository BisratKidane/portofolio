## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `colors.bg` `#f5f6fb` | Page background wash behind `/invitations` and `/register` (inherited `MuiCssBaseline` gradient, `theme.js:62-73`) |
| Secondary (30%) | `colors.paper` `#ffffff` | The switch card `Paper`, the confirmation `Dialog` surface, `AuthShell`'s card |
| Accent (10%) | `colors.primary` `#6366f1` / `colors.primaryDark` `#4f46e5` | See reserved list below |
| Destructive | **not used in this phase** | See below |

**Accent reserved for — exactly these four elements, nothing else:**

1. The `Switch` in its **checked (OPEN)** state — MUI default `color="primary"`, which paints thumb `colors.primary` and track a 50%-opacity primary. When CLOSED the switch is MUI's default grey. *The accent literally lights up when the door is open.*
2. The **`LockOpenRoundedIcon`** in the OPEN state — `sx={{ color: colors.primaryDark }}`.
3. The confirmation dialog's **"Open signup"** confirm button — `variant="contained"` default primary, which the theme paints with `colors.gradient` (`theme.js:81`).
4. On `/register`: the pre-existing `AuthShell` eyebrow, `BrandGlyph`, and "Sign in" link — **inherited, unchanged** (`AuthShell.jsx:26-30`, `Register.jsx:98-100`).

**Muted / non-accent state color:** `colors.slate` `#64748b` for the **`LockRoundedIcon`** in the CLOSED state and for all `text.secondary` copy. Not a new token (`theme.js:21,45`).

### Destructive: none — and this is a positive constraint, not an omission

Neither flip is destructive. Closing is instantly reversible; opening is instantly reversible. Therefore:

- `colors.error` `#ef4444` appears in this phase **only** inside `<Alert severity="error">` failure surfaces (MUI's own contrast-safe standardError treatment).
- The "Open signup" confirm button **must not** be `color="error"`. Red there would (a) misclassify a reversible setting change as irreversible and (b) dilute the red that `ApprovalsPage.jsx:194` genuinely reserves for the one irreversible commit on this page (rejecting a person). The dialog exists because opening is *consequential* (D-05), not because it is destructive.

### Contrast contract — verified, with the rejected options named

Every color that carries state meaning was checked against `colors.paper` `#ffffff`. This project already took a WCAG 1.4.11 finding (v4.0 WR-01, gender card rim at 2.97:1), so the math is recorded rather than assumed:

| Token | Hex | Ratio vs `#ffffff` | Verdict |
|-------|-----|--------------------|---------|
| `colors.ink` | `#0f172a` | ~17.9:1 | ✓ text + non-text |
| `colors.primaryDark` | `#4f46e5` | ~6.3:1 | ✓ text + non-text — **used for the OPEN icon** |
| `colors.slate` | `#64748b` | ~4.8:1 | ✓ text + non-text — **used for the CLOSED icon and all secondary text** |
| `colors.primary` | `#6366f1` | ~4.5:1 (4.47) | non-text only — **acceptable on the `Switch` track/thumb** (non-text, ≫3:1), **must not** be used as a text or icon color here |
| `colors.success` | `#10b981` | ~2.5:1 | ✗ **rejected** as a state carrier |
| `colors.warning` | `#f59e0b` | ~2.1:1 | ✗ **rejected** as a state carrier |
| `colors.error` | `#ef4444` | ~3.8:1 | non-text only — not used as a state carrier here |

**Why green/amber were rejected**, since a green-open / amber-closed indicator is the obvious first instinct: both fail 1.4.11's 3:1 minimum against the white card as a standalone non-text state carrier, *and* an outlined/filled MUI `Chip` at `color="success"` renders its label at `success.main` on white (2.5:1), failing 1.4.3 outright. Semantically they are also wrong: CLOSED is not a warning and OPEN is not a success — both are legitimate admin choices, and coloring them as good/bad editorializes a decision the admin is making deliberately.

### State is never carried by color alone

Four redundant cues, three of them non-color, so the OPEN/CLOSED state survives greyscale, colorblindness, and a screen reader:

1. **`Switch` thumb position** — checked = open (native `role="switch"` + `aria-checked`).
2. **Icon glyph shape** — `LockOpenRoundedIcon` vs `LockRoundedIcon`. Distinguishable at 1-bit.
3. **The literal headline text** — "Public signup is open" / "Public signup is closed".
4. Color — icon tint only, per the table above.

## States

### Switch region — five states, mutually exclusive

| State | Condition | Render |
|-------|-----------|--------|
| **Loading** | value not yet resolved, no load error | Region header renders normally. Inside the `Paper`, in place of the icon/headline/attribution/`Switch`: `<Stack direction="row" spacing={1.5} alignItems="center">` containing `<CircularProgress size={20} aria-hidden="true" />` + `<Typography variant="body2" color="text.secondary">Checking whether public signup is open…</Typography>`. **No `Switch` is rendered.** |
| **Open** | resolved `true` | `LockOpenRoundedIcon` (`colors.primaryDark`) · "Public signup is open" · attribution · `Switch checked` |
| **Closed** | resolved `false` | `LockRoundedIcon` (`colors.slate`) · "Public signup is closed" · attribution · `Switch` unchecked |
| **In-flight (mid-flip)** | a flip mutation is pending | `Switch` stays at its **pre-flip** position and is `disabled`; icon and headline unchanged; the attribution line is replaced by "Closing public signup…" / "Opening public signup…" |
| **Failed to flip** | the flip mutation rejected | `Switch` returns to its **last server-confirmed** position (never the attempted one). `<Alert severity="error" sx={{ mt: 2 }}>{actionError}</Alert>` rendered inside the `Paper`, below the switch row. Then **re-read the setting**. |
| **Failed to load** | the initial read rejected | In place of the switch row: `<Box sx={{ display: 'flex', flexDirection: 'column', gap: 2, alignItems: 'flex-start' }}>` with `<Alert severity="error">{loadError}</Alert>` + `<Button variant="contained" sx={{ minHeight: 44 }}>Retry</Button>`. **No `Switch` is rendered.** |

**No shape here is invented.** Every one is carried over with a citation:

- `CircularProgress` at a region-appropriate size with `aria-hidden="true"` — the exact idiom at `GenerationGrid.jsx:77-81` (`size={16}`, `aria-hidden="true"`). This region uses `size={20}` to sit on the 20px `h6` line it replaces; the component, the a11y attribute, and the inline (non-page-centered) placement are all pre-existing. The page-centered `py: 8` treatment at `ApprovalsPage.jsx:109` is deliberately **not** reused — this is a region inside a page, not a page.
- The error+Retry pair is verbatim `DetailPage.jsx:198-206` (and the same shape at `FamilyTreePage.jsx:~100-105`). `minHeight: 44` on the button matches `FamilyTreeCanvas.jsx:455`.
- The load-error / action-error split is exactly `ApprovalsPage.jsx:46-47`'s `loadError` / `actionError`, which Phase 33's code review (WR-01) introduced precisely so one failed action cannot blank the whole surface. Carry the split; do not regress to a single `error`.
- Re-reading after a failed flip mirrors `ApprovalsPage.jsx:70-74`'s `await load()` in the catch — added for that same WR-01 — and matters more here: two admins in an incident can flip in opposite directions, and a lost race must be refreshed away rather than left showing a stale state next to a live control.

**Why no `Switch` renders in the Loading and Failed-to-load states.** The thumb position is the primary state signal. Rendering it in an arbitrary position before the value is known asserts a state that may be false — an admin could read "closed" while the door is open, which is a direct ADMIN-03 violation on the one surface ADMIN-03 governs. Showing nothing is honest; showing a guess is not.

**Why the flip is never optimistic.** D-07's hard constraint is that the client and server must not hold independently-derived notions of "enabled". An optimistic flip creates exactly that: a rendered `OPEN` that no server value backs. The constraint applies to the write path as much as the read path.

| **Open** | resolved `true` | The Phase 33 signup form, **completely unchanged** (`Register.jsx:89-193`) |
| **Closed** | resolved `false` | `renderInvitationOnly()` |
| **Mid-form refusal swap** | a tokenless submit was refused **and** a re-read now returns `false` | `renderInvitationOnly()` — the identical render. Any error `Alert` is cleared first. |
| *(unchanged)* | `token` present | The invited form, untouched, rendered immediately with no query gate (D-08) |

**Why the loading state shows no chrome.** Every visible word differs between the two outcomes — eyebrow, title, subtitle, and body all change. There is no honest neutral chrome. One spinner for one cheap unauthenticated round-trip is strictly better than rendering "Create your account" with four input fields and then yanking them away, which on a security-adjacent surface reads as a malfunction and erodes trust in the very moment the switch is doing its job.

### The mid-form refusal — how the UI decides, and what it must not do

**Detection contract:** on a rejected tokenless submit, **re-run the `publicRegistrationEnabled` query**. If it now returns `false`, swap to `renderInvitationOnly()`. Otherwise, render the error in the top-of-form `<Alert severity="error">` exactly as today (`Register.jsx:105`).

**Explicitly forbidden: matching on the server's refusal message string.** A string match would give the client a second, independently-derived notion of "the door is closed" — decoupled from the stored value, silently broken by any rewording of the server message, and untestable against the real predicate. That is the precise bug class D-07 names and that has now hit this project across Phases 14, 15, 30, 31, 32 and 33. Re-querying keeps both branches reading the same stored value through the same accessor.

(`graphqlRequest` flattens GraphQL errors to `new Error(messages.join('\n'))` at `graphqlClient.js:26-28`, so `extensions.code` is not reachable without changing the shared client. The re-query is both the safer and the cheaper option; do not widen `graphqlClient.js` for this.)

**The swapped view is the SAME message, not a second variant.** Do not add "the door just closed while you were filling this in", do not add a "your details weren't saved" line, do not add a distinguishing `severity`. Two reasons:

1. A second variant is copy that must stay in sync with the first and will not.
2. A message that differs by *how* the visitor arrived leaks that an admin closed the door in the last few seconds — timing information about an administrative action, on a public unauthenticated page.

Losing what the visitor typed is accepted: there is nothing left to submit it to.

### Date formatting

Attribution dates use `toLocaleDateString(undefined, { day: 'numeric', month: 'short', year: 'numeric' })` → "8 Sep 2026" — the existing provenance format at `AdminMemberTable.jsx:21-26`. Not `ApprovalsPage.jsx:37-42`'s `toLocaleString` variant, which appends a time ("8 Sep 2026, 14:32"); a setting that may sit unchanged for months does not need minute precision. D-06's example reads "on 8 Sep"; the year is included deliberately, because this state can plausibly go a year without changing and a bare "8 Sep" would then be ambiguous.
