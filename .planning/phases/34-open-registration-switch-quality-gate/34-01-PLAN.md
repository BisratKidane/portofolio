- **RESEARCH Open Question 1 — boot-time assert for migration 021: NO.** `initializeDatabase()` runs `sequelize.sync()` at `models/index.js:121` *before* `assertRequiredColumns(sequelize)`, and `sync()` creates missing tables — so a table-existence assert is dead code by construction. A *row*-existence assert would crash the backend in exactly the state D-02 says must fail closed rather than fail loudly. Signals instead: the accessor's one-line `console.warn` on an absent row, the README 021 section, and the admin UI reading "Public signup is closed — Not changed since setup." Do NOT add an entry to `backend/src/config/assertRequiredColumns.js`.
- **CONTEXT F-01 — audit row vs denormalized columns: BOTH.** `app_settings` carries `updatedAt`/`updatedById` as a display convenience (this plan) **in addition to** the `AuditLog` row written on every flip (plan 34-03), written atomically in one transaction. D-01's own locked shape already contains those columns; D-03's ban is specifically on dropping the audit row *in favour of* them. Nothing is dropped.
- **CONTEXT D-01 correction — the column is `settingKey`, not `key`.** `KEY` is a reserved word in the MySQL 8.4 keyword table; `CREATE TABLE app_settings (key VARCHAR(64) ...)` is a syntax error in hand-written SQL. D-01 explicitly delegates the exact naming to Claude's discretion, so this is a correction inside an already-granted discretion, not a decision reversal.
