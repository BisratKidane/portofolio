<objective>
Make `/register` show the right surface: the signup form when the door is open, the invitation-only message when it is closed — including when it closes while someone is mid-form.

Purpose: ADMIN-02's first clause. The dangerous part is the tier boundary: the client *renders* a decision the server made and never makes one itself. `34-UI-SPEC.md` forbids string-matching the server's refusal message outright, because that would give the client a second, independently-derived notion of "the door is closed" — decoupled from the stored value, silently broken by any rewording, and untestable against the real predicate. Re-querying keeps both branches reading the same stored value through the same accessor.

Output: the gate, the loading state, one `renderInvitationOnly()` with two call sites, the re-query swap, and the tests for all four states. Plan 34-02 already migrated this test file's harness so this plan's diff is the feature and nothing else.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous visitor's browser -> `/graphql` | The visitor controls everything the client sends; the client's only job is to render a decision the server made |
| server refusal message -> client control flow | The tempting-but-wrong design; moving the predicate into the browser is the same tier error D-07 names |
| invited visitor (token in URL) -> the gate | Must not cross it at all (D-08) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-06-A | Elevation of Privilege | client-side-only enforcement | accept (server is the gate) | The `/register` surface is presentation; the actual refusal is `register`'s server-side check (plan 34-05) and is proven independently by the SEC-04 matrix (plan 34-07). A visitor who bypasses the UI entirely still gets refused |
| T-34-06-B | Elevation of Privilege | outer/inner guard divergence at the tier boundary | mitigate | The client never derives "closed" from the refusal text; it re-runs `publicRegistrationEnabled`, so both branches read the same stored value through the same server-side accessor. A grep gate asserts no `err.message.includes/===/match` in non-comment lines, and test 7 (an unseen rejection message still swaps) is the behavioural pin |
| T-34-06-C | Information Disclosure | timing leak about an administrative action | mitigate | The swapped view is byte-identical to the initial-closed view — no "the door just closed while you were filling this in" variant — so a visitor cannot learn that an admin acted in the last few seconds |
| T-34-06-D | Spoofing | asserting a state before it is known | mitigate | The loading state paints no chrome and no form; `publicOpen === null` is a distinct third value, not a boolean default that would pick a side |
| T-34-06-E | Denial of Service | invited registration blocked by a failed public read | mitigate | The query is guarded on `!token`, so the invited branch never issues it and never waits on it (D-08); plan 34-02's synchronous invited test is the regression pin |
| T-34-06-F | Business Logic | a network failure silently opening the door | mitigate | A rejected read sets `publicOpen` to `false`, matching the server's D-02 fail-closed default, so the two sides never disagree in the direction that exposes the form |
| T-34-06-SC | Tampering | npm installs | accept | Zero new packages |
</threat_model>
