<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `register`'s public API contract vs. any client assuming the old `{token, user}` shape | This is a deliberate, breaking contract change (D-10) — the frontend's `AuthContext` is updated in lockstep by Plan 11-06 |
| `login`'s error-ordering | Revealing "unverified" only after password validation avoids leaking account existence via a distinct error message before credentials are checked |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-04a | Elevation of Privilege | `register`'s ADMIN assignment | mitigate | ADMIN assignment removed entirely from `register` (Task 1) — proven by a dedicated regression test asserting the first-ever registrant gets `role: 'USER'`. The actual race-safe assignment lands in Plan 11-05's `verifyEmail`. |
| T-11-04b | Information Disclosure | `login`'s unverified-account message | mitigate | The unverified message only fires after password validation succeeds (Task 2, Test 3 proves ordering) — an attacker cannot use it to distinguish "wrong password" from "unverified account" for a guessed email without already knowing the correct password. |
| T-11-04c | Tampering (token) | `register`'s verification token | mitigate | `createVerificationToken()` (crypto.randomBytes(32)) generated fresh per registration; only `hashVerificationToken()`'s sha256 output is persisted; the raw token is only ever handed to the mailer, never returned in the GraphQL response (Test 1/3 in Task 1 prove the response has no token field and the hash-vs-raw separation). |
</threat_model>
