<objective>
Expose the recursive family-graph shape over GraphQL for the first time — `mother`, `father`,
`spouses`, `children`, `siblings`, and `linkedUser` on the `FamilyMember` type — wired entirely
through the `createLoaders(models)` factory from 14-01 so resolved SQL query count stays flat
regardless of tree depth or width, and prove both halves of SC-5 (flat query count, and a real
recursive-field depth-limit rejection) with dedicated fixtures.

Purpose: this is the read-side surface every later mutation plan's tests will query against to
assert relationship state, and the load-bearing proof that D-07/D-08's Wave-1 infrastructure
actually prevents N+1/DoS on real data, not just synthetic introspection queries.
Output: extended `familyMember.schema.js`/`familyMember.resolver.js`; a reusable
`buildGenerationFixture` test factory; the SC-5 query-count + depth-limit integration tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Recursive GraphQL field resolution (`children`/`spouses`/`siblings`) over a self-referencing type | Exposed to any `requireFamilyAccess`-gated caller; traversal depth/width is client-query-controlled |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-07 | Denial of Service | `children`/`spouses`/`siblings` field resolvers | mitigate | All three route through the request-scoped loaders built in 14-01; `familyMember.queryCount.test.js` enforces the flat-query-count bound as a regression gate |
| T-14-06 | Denial of Service | `maxDepthRule` validation | mitigate | Same rule from 14-01, now proven against a real recursive field (`children`) rather than only introspection |

No new Elevation-of-Privilege surface is introduced here: read access to these fields is gated
identically to the existing `familyMember`/`familyMembers` queries via `requireFamilyAccess` at
the query root; nested field resolvers inherit the same authenticated context and expose no
additional write capability.

</threat_model>
