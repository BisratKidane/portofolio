<objective>
Build the Apollo plugin that turns the Plan 10-01 store into an actual enforcement guard, and wire the production server (`server.js`) to trust exactly one reverse-proxy hop and register the plugin. The plugin's field-identification logic reads the parsed GraphQL operation AST (`operation.selectionSet.selections`) rather than the client-supplied `operationName` string — this is the deliberate, security-driven design choice that closes an operation-renaming/anonymizing bypass of the limiter, which the client-string approach sketched in PATTERNS.md would not have closed.

Purpose: This is the crux of the phase's security value — a limiter that trusts the wrong signal for either "who is calling" (IP) or "what are they calling" (operation) is trivially bypassable. `trust proxy = 1` bounds the first; AST-based field extraction bounds the second.
Output: `enforceRateLimit(clientIp, fieldNames)` and `rateLimitPlugin`, TDD-proven in isolation; `server.js` trusting one proxy hop, deriving `clientIp`, and registering the plugin on its ApolloServer instance; an HTTP-level test proving IP-spoof resistance; a new README section documenting the trust boundary (D-04).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Internet -> reverse proxy (1 hop, Nginx/Caddy) -> Express `trust proxy = 1` -> `req.ip` -> `contextValue.clientIp` -> rate-limit key | Everything to the left of the single trusted proxy hop is attacker-controlled; `req.ip` is the only point where that boundary is enforced. |
| GraphQL request document -> `operation` AST -> field-name extraction -> rate-limit key | The client fully controls the request document, including any operation name or alias; only the actual selected field names (not the declared operation name) are trustworthy signals of "what is being called." |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-02a | Spoofing (IP spoofing via forged `X-Forwarded-For`) | `server.js` `trust proxy` config -> `req.ip` | mitigate | `trust proxy = 1` honors only the single nearest-hop address; any additional forged prefix entries are ignored by Express/`proxy-addr`. Proven by `server.trustProxy.test.js` (Task 2). |
| T-10-02b | Tampering (rate-limit bypass via renamed/anonymous GraphQL `operationName`) | `rateLimitPlugin.js` `didResolveOperation` | mitigate | Field identification uses `operation.selectionSet.selections[].name.value` (the parsed AST), never `requestContext.operationName` (the client-supplied string) — `enforceRateLimit`'s isolation-by-field-key logic is proven directly in Task 1; the full AST-extraction path is proven end-to-end in Plan 10-03. |
| T-10-02c | Information Disclosure (enumeration oracle via a differential 429) | `enforceRateLimit` | mitigate | The guard throws before any resolver executes, with a single fixed message and exactly one extensions field (`code`) — no count, timing hint, or account-existence signal. TDD-proven in Task 1; the required real-vs-nonexistent parity test is deferred to Plan 10-03, which has access to the real `login`/`register`/`requestPasswordReset` resolvers. |
| T-10-02d | Denial of Service (per-IP limiting collectively throttles multiple legitimate users behind one NAT/corporate egress IP) | design-level, not a specific file | accept | Per-IP (not per-account) limiting is the explicit, locked milestone choice (D-01); per-account limiting, CAPTCHA, and escalating lockout are explicitly deferred (CONTEXT.md Deferred Ideas). Accepted collateral risk of the chosen mitigation strategy, not a defect. |
</threat_model>
