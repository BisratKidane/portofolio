## Approval Queue Card Composition (D-07/D-08 — the highest-risk surface)

Replaces `ApprovalsPage.jsx`'s existing row rendering. The current file already uses `Paper`-per-row (not a literal MUI `Table` — the true `Table` this diverges from is `AdminMemberTable.jsx`, used by `ManagePage.jsx`), but its internal layout is a horizontal header/actions split. **D-07 requires a vertical composition** — header, then body, then footer, stacked — which this phase must restructure to.

**Container (per card):**
```
Paper
  elevation={0}
  sx={{ p: { xs: 2.5, md: 3 }, borderRadius: 4, border: `1px solid ${colors.line}` }}
```
(Exact values carried over from the current `ApprovalsPage.jsx` Paper — do not invent new radius/border values.)

**Vertical structure inside each card, top to bottom:**

1. **Header** — `Stack spacing={0.5}` (4px)
   - Name: `Typography variant="h6"` (20px/700) — no `noWrap`; the vertical layout has full card width, truncation is not needed here
   - Email: `Typography variant="body2" color="text.secondary"` (14px/400)

2. **Gap:** 16px (`md`) before the note block.

3. **Body — the relationship note** (design risk #2):
   - Label: `Typography variant="overline" color="text.secondary"` — text **"Relationship note"**
   - Panel: `Box sx={{ mt: 0.5, p: 2, borderRadius: 3, backgroundColor: colors.bg, maxWidth: { xs: '100%', sm: 640 } }}` — the page-background tint (`#f5f6fb`) used as an inset "quoted" well, distinguishing free text from the white card surface without inventing a new color token. `maxWidth: 640` (≈65ch at 16px) keeps the paragraph's line length readable regardless of how wide the card itself is.
   - Text: `Typography variant="body1" sx={{ lineHeight: 1.6, whiteSpace: 'pre-wrap' }}` — plain string interpolation only (React's default escaping is sufficient per SEC-03; **never** `dangerouslySetInnerHTML` or markdown rendering on this field). Full text always shown — no truncation, no `noWrap`, no `-webkit-line-clamp`, no "show more" affordance, no `max-height`+`overflow`.
   - **Empty state** (note is null/empty — a normal state per D-08, not an error): same label, same panel styling, text becomes `Typography variant="body1" color="text.secondary"` reading **"No note provided."** — never omit the block entirely (the old `Field` helper in `ApprovalsPage.jsx` returned `null` for falsy values; that pattern must not carry over for this field).

4. **Divider:** `Divider sx={{ my: 2, borderColor: colors.line }}` — the one deliberate hard visual boundary on the card, separating judgment content (name/email/note) from action controls.

5. **Footer** — `Stack direction={{ xs: 'column', sm: 'row' }} justifyContent="space-between" alignItems={{ xs: 'flex-start', sm: 'center' }} spacing={1.5}`:
   - Left: `Typography variant="body2" color="text.secondary"` — **"Registered {formatWhen(createdAt)}"** (reuse `formatWhen` from `ApprovalsPage.jsx` unchanged)
   - Right: `Stack direction="row" spacing={1.5}` —
     - **Approve** — `Button variant="contained" color="success" startIcon={<CheckCircleRoundedIcon/>}` — text "Approve"
     - **Reject** — `Button variant="outlined" color="error" startIcon={<CancelRoundedIcon/>}` — text "Reject", opens the confirm dialog

**Card-to-card spacing:** `Stack spacing={3}` (24px) between cards — wider than the current 16px row gap, because these cards are now variable-height (D-08) and need a clearer separation cue than a tight table-row rhythm would give. The `Paper` border+radius already gives each card a hard boundary regardless of height, so 24px is a comfortable, not excessive, gap.

### Visual weight ladder for the destructive action (design risk #3)

Three escalating tiers, never skip a tier:

1. **At rest:** Approve is `contained` + `success` green (high emphasis, inviting) — Reject is `outlined` + `error` red (present, but visually quieter — an outline, not a fill).
2. **On Reject click:** opens a dialog (D-09) — no destructive action fires yet. Dialog's own "Cancel" is a plain text button (lowest emphasis, the easy way out); the dialog's "Reject" confirm button is the *only* place `contained` + `error` red (highest emphasis, filled) appears in this whole surface — reserved exclusively for the irreversible commit.
3. **Reason field** inside the dialog is explicitly optional (D-09) — label reads "Reason (optional)", nothing blocks submission when empty.

### Scannability at scale (the D-07/D-08 tension)

With note length varying 0–500 characters, cards will be visibly different heights. The mitigation is typographic, not structural: every card's **header** (name, 20px/700) sits at the same position relative to the card's top edge and reads at a consistent size regardless of note length, so an admin scanning down a long queue can track names alone without reading every note, then drop into whichever note actually needs reading. Do not compress header spacing to "save space" on cards with long notes — the header's fixed rhythm is what keeps the list scannable.

### Data model simplification (D-10)

`pendingApprovals` returns flat `User` rows (`id name email relationshipNote createdAt`) directly — there is no `registeredUser` indirection to null-check. The current `ApprovalsPage.jsx`'s `orphaned`/`blocked`/`Tooltip` disabled-reason logic exists only because the old invitation-shaped query could return a row whose `registeredUser` was null (`ON DELETE SET NULL`). That entire code path is dead weight once the query swaps to `pendingApprovals` — remove it, do not carry it forward. Every row rendered is by definition an actionable account.

## States (SC-5 — loading, empty, failed must all render through existing components)

The current `load()` implementation has a latent gap: on query failure, `rows` stays `null` forever, so the `CircularProgress` spinner and the error `Alert` render simultaneously and indefinitely. This phase must resolve the three states as mutually exclusive:

| State | Condition | Render |
|-------|-----------|--------|
| Loading | `rows === null && !error` | `<Box sx={{ display: 'flex', justifyContent: 'center', py: 8 }}><CircularProgress /></Box>` — reused verbatim from `ApprovalsPage.jsx` |
| Failed | `error` is truthy (regardless of `rows`) | `<Alert severity="error">{error}</Alert>` only — no spinner, no empty panel, no card list underneath |
| Empty (success) | `rows !== null && !error && rows.length === 0` | `<Paper elevation={0} sx={{ p: 4, borderRadius: 4, border: '1px solid ' + colors.line, textAlign: 'center' }}>` containing the empty-state heading + body copy above |
| Populated (success) | `rows !== null && !error && rows.length > 0` | The card `Stack` described above |

The page header ("Pending approvals" title + description) renders unconditionally above all four states — it is never itself part of the empty/loading/failed panel, so the page never looks broken even mid-failure.

**Page description copy** (replaces the current "Review family members who registered via invitation..." line, which is now inaccurate per D-10 — the queue holds only self-registrants, not invitees): **"People who signed up on their own and verified their email, waiting for a decision on whether they're family."**

Pre-populated from: CONTEXT.md's discretion grant ("carry the established shapes over... rather than inventing new ones") + SC-5 (ROADMAP.md) + observed gap in current `ApprovalsPage.jsx`.

## Signup Form Validation Contract (D-04 — design risk #4: four fields, no wall of red)

**Timing rule (the anti-wall-of-red mechanism):** validate a field on `blur`, not on every keystroke, for its first error. Once a field has been touched and is showing an error, re-validate on every subsequent keystroke so the error clears the instant it's fixed. On submit, mark all four fields as touched at once (so a submit with multiple invalid fields lights all of them up together) — this is the only moment several inline errors may appear simultaneously, and each message is one short line to keep total vertical footprint low.

**Mechanism:** MUI `TextField`'s native `error` + `helperText` props only — no custom error banner component, no icons added beyond what `TextField` already renders. This keeps each error visually small (12px caption-weight helper text + a red field outline) rather than a full-width red `Alert` per field.

**Strict separation of concerns:** the top-of-form `<Alert severity="error">` is reserved *exclusively* for server-side errors returned after a submit attempt (network failure, or anything the client-side checks didn't catch). It must never duplicate a message already shown inline on a field — inline = client-side, top `Alert` = server-side backstop. This is the direct interaction-level expression of D-04's "client-side first, server as backstop."

**Per-field rules and exact copy** — copied verbatim from the backend policy modules' own messages where a server equivalent exists, per D-04's constraint that client rules must not be independent, more-permissive approximations of the server's:

| Field | Rule | Error copy | Server source (for parity) |
|-------|------|-------------|------------------------------|
| Full name | required; ≤255 chars | "Enter your name." / "Name must be 255 characters or fewer." | `backend/src/utils/namePolicy.js` (`MAX_NAME_LENGTH = 255`) — message copied verbatim |
| Email address | required; valid format; ≤254 chars | "Enter your email address." / "Enter a valid email address." / "Email must be 254 characters or fewer." | `backend/src/utils/emailPolicy.js` (`MAX_EMAIL_LENGTH = 254`, `isEmail`) — messages copied verbatim |
| Password | required; ≥8 chars | "Password must be at least 8 characters." | `backend/src/utils/passwordPolicy.js` — message copied verbatim (no strength meter — explicitly deferred, see REQUIREMENTS.md history) |
| Relationship note | required on the public path only (D-03); ≤500 chars | "Tell us how you're related to the family." / "Relationship note must be 500 characters or fewer." | `backend/src/utils/relationshipNotePolicy.js` (500-char cap only — the "required" rule itself is UI-only, since the backend leaves the note optional per Phase 32 D-06) |

**Constraint the planner/executor MUST honour (repeating D-04's explicit warning):** these four thresholds (255 / 254 / 8 / 500) must stay numerically pinned to the backend policy modules above. Since frontend and backend are separate npm workspaces, a literal cross-workspace `import` may not be practical — at minimum, declare the frontend constants with an inline comment citing the exact backend file, and add a colocated test that fails loudly if the numbers ever drift apart. This is the exact bug class (CR-01, 32-REVIEW.md) that must not repeat.

**Relationship note field composition:** `TextField multiline minRows={3}` with a two-part `helperText` node — left side shows the default hint / active error message, right side shows a live character counter ("142/500") in `Typography variant="caption" color="text.secondary"`, switching to `color="error"` only once the 500-char cap is exceeded (the counter itself is not an error until then).

Pre-populated from: D-04 (locked, including its explicit anti-regression warning) + backend policy module source (read directly) + REG-01 (required fields).
