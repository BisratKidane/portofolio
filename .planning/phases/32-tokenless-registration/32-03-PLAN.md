<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Public internet → `register` mutation (no auth required) | Fully untrusted input crosses here: `name`, `email`, `password`, `relationshipNote`, and (on the invited branch) `token`. |
| `register`'s tokenless branch → `sendRegistrationAttemptEmail` | Reads the resolved existing account's OWN stored email/name, not the caller's argument — the boundary between "what the caller sent" and "who actually gets notified" is the `models.User.findOne` lookup, not the request. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-32-07 | Spoofing | `register` (tokenless branch) | mitigate | The created account's identity is always the caller-normalized email they themselves supplied, and it must still be proven by email verification before anything trusts it — no elevated trust is granted before verification+approval (unchanged two-gate model). |
| T-32-08 | Information Disclosure (user enumeration) | `register` (tokenless branch), taken vs free outcome | mitigate | Identical response message on both outcomes (D-08) plus bcrypt computed before the lookup so response timing does not diverge on the specifically-named oracle (D-09) — closes both the message-content and timing halves of SEC-01. |
| T-32-08b | Information Disclosure (timing, residual) | `register` (tokenless branch), taken vs free outcome | accept | The free path's extra `User.create` write costs low-single-digit ms versus bcrypt's ~100ms; this residual skew is accepted as impractical to exploit — it is not the oracle CONTEXT.md names (bcrypt, not the write). |
| T-32-09 | Elevation of Privilege | `register` (invited branch) with a hostile `email` argument | mitigate | The invited branch's local `const email = invitation.invitedEmail` shadows the caller-supplied `email` argument, so a caller cannot redirect Phase 31's auto-activation vouch to an address the admin never approved — proven by the D-02 adversarial test (valid token + hostile email still lands at `invitedEmail`). |
| T-32-10 | Tampering | Plan 32-01's `beforeCreate` bcrypt guard, exercised via D-09's precomputed-hash create call | mitigate | Already mitigated at the model layer in Plan 32-01; this plan's login-with-original-password test is the end-to-end proof the guard holds under real resolver usage, not just the isolated model-hook test. |
| T-32-11 | Denial of Service (approval-queue flooding / brute-force probing) | `register` (tokenless branch) | mitigate | Inherits the existing per-IP register rate limit (5/hour) by construction, since D-01 keeps a single `register` GraphQL field — proven by SEC-02's dedicated test, not argument alone. |
| T-32-12 | Repudiation / spam vector | `sendRegistrationAttemptEmail` (D-10) | mitigate | Fires only to `models.User.findOne`'s resolved existing-account email, never to the caller-supplied argument directly, so it cannot be abused to spam an arbitrary address with no account. |

No package installs occur in this plan (`bcryptjs` is an existing direct dependency already used elsewhere in this codebase — no `T-32-SC` row needed).
</threat_model>
