<objective>
Close 32-VERIFICATION.md's Gap 3 (Truth 8, new this round / 32-REVIEW.md CR-02 second-round numbering): the tokenless register branch pre-validates `relationshipNote` and `name` OUTSIDE the guarded try/catch specifically so their failures produce an actionable error instead of being converted into the uniform success message -- but `email` gets only a truthiness check (`if (!email) throw ...`). Format (Sequelize's `isEmail` validator) and length (the `VARCHAR(255)` column) are left to the model layer, which throws INSIDE the try block and is swallowed by the catch-all into the identical success message. Reproduced in 32-VERIFICATION.md: registering with `email: "ada@exmaple"` (a plain missing-TLD typo) returns the success message with zero rows created and no signal to the registrant.

Purpose: give `email` the same pre-try, actionable-error treatment `name` and `relationshipNote` already get, closing the single most common registration failure mode this codebase's own `assertRequiredColumns.js` docblock calls unacceptable ("silently accepting and dropping every self-registration forever") -- while explicitly NOT touching the taken-email enumeration-silence guarantee (SEC-01/D-08), since email format depends only on the caller's own input, never on account state.

Output: a new `backend/src/utils/emailPolicy.js` utility (`assertRegistrationEmail`) mirroring `namePolicy.js`'s shape, wired into the tokenless register branch before the try block, with unit and integration regression coverage.
</objective>

```
export const MAX_NAME_LENGTH = 255;

export function assertRegistrationName(name) {
  const trimmed = String(name ?? '').trim();
  if (!trimmed) throw new Error('Name is required.');
  if (trimmed.length > MAX_NAME_LENGTH) throw new Error('Name must be 255 characters or fewer.');
  return trimmed;
}
```

```
  validate: { isEmail: true }
}
```
