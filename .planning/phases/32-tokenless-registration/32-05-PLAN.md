<objective>
Close the one blocking gap from 32-VERIFICATION.md: CR-01, an unauthenticated account-enumeration oracle in `register`'s tokenless branch. The taken-email path always returns a fixed success message with no DB write; the free-email path falls through to an unguarded `models.User.create(...)` whose failures (over-length `name`, a duplicate-insert race, or — on an unmigrated target — a missing-column error) surface as raw GraphQL errors. This single-request, deterministic divergence defeats SEC-01/D-08 outright and was independently reproduced live by the verifier against the test database.

This plan validates `name` (trim, require non-empty, cap at 255 — mirroring `passwordPolicy.js`'s guard-clause idiom) *before* the existing-user lookup, wraps the free-email `User.create` call in try/catch so any create failure returns the identical success message instead of leaking ORM/DB error text (also closing WR-02), and applies a `MIN_REGISTER_RESPONSE_MS` response-time floor — mirroring `requestPasswordReset`'s existing `MIN_RESET_RESPONSE_MS` idiom in this same file — to close the residual ~1.3ms timing divergence (WR-01). The fix is proven RED-before-GREEN: the regression test reproducing CR-01's exact 300-character-name payload is written and observed failing against the current code before the resolver changes land, per this project's repeated lesson that a fully green suite can coexist with a live enumeration defect (see `register.test.js`'s pre-existing test at line 179, which only asserted the message string for well-formed input).

The invited registration branch (`if (token) { ... }`) is explicitly NOT touched by this plan. SEC-01/D-08 scopes enumeration-silence to the tokenless path alone — reaching the invited branch already requires a valid, unused, unexpired invitation token, so it is not an equivalent anonymous oracle. WR-03's residual half (blank/whitespace-only `name` still accepted on the invited branch) stays open as documented debt; only the tokenless half is closed here, as the gap-closure scope permits.

Purpose: make Phase 32's Success Criterion 2 ("An email that already has an account gets a response indistinguishable from one that does not") actually true under adversarial input, not just well-formed input.
Output: `backend/src/utils/namePolicy.js` (new), a hardened tokenless `register` branch in `backend/src/resolvers/user.resolver.js`, and regression coverage in `backend/src/resolvers/register.test.js` plus two new dedicated policy-module test files.
</objective>
