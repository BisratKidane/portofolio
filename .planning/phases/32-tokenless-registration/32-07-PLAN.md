<objective>
Close BLOCKER 1 (CR-01) from 32-VERIFICATION.md / 32-REVIEW.md: Phase 32 opened `register` to
anonymous callers with no feature flag (D-03, locked). That removed the only thing that made
`verifyEmail`'s pre-existing zero-admin ADMIN-bootstrap safe -- before Phase 32, reaching
`verifyEmail` at all required an admin-issued invitation token (Phase 13 through Phase 31). Two
confirmed-reachable windows now exist: (a) a fresh deployment, where the first anonymous verifier
(attacker or operator, whoever wins the race) claims the ADMIN role, and (b) an existing
deployment, where `updateUser` lets the sole verified admin change their own email --
unconditionally setting `emailVerified = false` -- with no last-administrator guard on that path
(the guard only covers role changes), transiently reopening the zero-admin window to the internet.

This plan closes both windows without deleting the bootstrap or adding a `register`-gating
feature flag (D-03 forbids that; this plan does not touch `register` at all). The safe path to a
first admin becomes `ADMIN_EMAIL`, an optional env var: the zero-admin bootstrap now promotes
ONLY the account whose email matches `env.adminEmail`, and fails closed (promotes nobody) when
`ADMIN_EMAIL` is unset. This is not a new invention -- it is Phase 11's own VERIFY-F1
("env-seeded ADMIN_EMAIL as belt-and-suspenders"), deliberately deferred at the time because
"the D-03 admin-row grandfather covers the deploy case... revisit if multi-environment admin
bootstrapping becomes a need" (`11-CONTEXT.md`). Phase 32 created exactly that need.

Purpose: make the zero-admin bootstrap unreachable by an anonymous, unvouched tokenless
registrant, while preserving one explicit, documented, testable path for a real operator to
become the first admin.
Output: `env.adminEmail`, a gated `verifyAndPromote` bootstrap, an extended `updateUser`
last-administrator guard, regression + mutation-test coverage for both, and a corrected
README.md bootstrap description.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| anonymous internet -> `register` (tokenless) -> `verifyEmail` | An unauthenticated caller can create an account and, by verifying an email they control, reach the zero-admin bootstrap decision point. This boundary already exists from Phase 32; this plan changes only what happens on the far side of it. |
| authenticated self/admin -> `updateUser` | A logged-in user (self) or an admin (any target) can trigger the email-change path that this plan gates. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-07-01 | Elevation of Privilege | `verifyEmail`'s zero-admin bootstrap (`user.resolver.js`) | mitigate | Gate the promotion on `env.adminEmail` match; fails closed (promotes nobody) when unset, per Task 1. |
| T-32-07-02 | Elevation of Privilege | `updateUser`'s email-change path (`user.resolver.js`) | mitigate | Extend the last-administrator guard to cover de-verification via email change, per Task 2. |
| T-32-07-03 | Information Disclosure | `env.adminEmail` value | accept | Operator-controlled config, never returned in any GraphQL response or log line this plan adds; same handling class as `jwtSecret`/DB credentials already in `env.js`. |
| T-32-07-SC | Tampering | npm/pip/cargo installs | accept | This plan installs no new packages. |

## Residual Risks Explicitly Left Open

- CR-02 (32-REVIEW.md: no email format/length validation on the tokenless path, so a malformed address silently returns success with no account created) is NOT addressed by this plan -- it is outside this gap-closure round's declared scope (32-VERIFICATION.md names only CR-01 and CR-03 as blockers for this round).
- Unifying the codebase's four divergent "admin" definitions (Phase 31 WR-03) remains explicitly out of scope, as it has been since Phase 31-05.
- A truly adversarial fresh-deployment race (an attacker who discovers the URL and registers before the operator sets `ADMIN_EMAIL` and registers themselves) is not eliminated by this plan -- it is narrowed to "the attacker's email must equal the operator's chosen `ADMIN_EMAIL`", which is not guessable, versus the pre-fix "whoever verifies first, unconditionally". Deployment-timing discipline (configure `ADMIN_EMAIL` and register before publicizing the URL) remains part of the operational model, consistent with D-03's existing framing.
