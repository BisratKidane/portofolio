<objective>
Give a self-registrant's relationship note somewhere to live on the `users` table (D-04), and close the single highest-risk defect identified for this phase before any resolver code depends on it: `User.js`'s `beforeCreate` hook unconditionally re-hashes `passwordHash` with no already-hashed guard, so Plan 32-03's D-09 (precompute the bcrypt hash before the existing-user lookup, then pass the precomputed hash into `User.create`) would otherwise silently double-hash every self-registered password and lock the person out of their own account at first login. The guard is driven by an explicit `options.passwordAlreadyHashed` flag set only by trusted internal callers — never by inspecting `passwordHash`'s content or shape, which would let an attacker-chosen password that happens to look like a bcrypt hash bypass hashing entirely and be stored in cleartext.

Purpose: this is pure foundation — no resolver logic changes here. It exists so Plan 32-03 can build the tokenless `register` branch directly against a working column and a working hook, instead of discovering the double-hash defect mid-implementation.
Output: `backend/migrations/manual/020-add-users-relationship-note.sql` (proven on a scratch DB, then applied by hand to local dev), an updated `backend/src/models/User.js`, and regression tests in `backend/src/models/User.test.js`.
</objective>

    Fix the `beforeCreate` hook (currently `async beforeCreate(user) { if (user.passwordHash) user.passwordHash = await bcrypt.hash(user.passwordHash, 12); }` — unconditional, unlike `beforeUpdate`'s `changed()` guard) using an explicit, non-content-derived control channel — NOT content-sniffing. A prior version of this plan proposed a `BCRYPT_HASH_PATTERN` regex test against `passwordHash`'s shape; that is rejected here because a self-registrant who chooses a real password that happens to start with a bcrypt-format prefix (e.g. `$2a$04$aaaaaaaaaaaaaaaaaaaaaa`, 22+ chars, trivially passes `assertPasswordStrength`'s length check) would have that password persisted verbatim in cleartext, silently, with no error — a worse defect than the double-hash bug being fixed.

    Instead, use Sequelize's `options` argument, which every hook receives as its second parameter: `beforeCreate(instance, options)`. Confirmed against the installed `sequelize@6.37.8` (`node_modules/sequelize/lib/model.js` and `node_modules/sequelize/lib/hooks.js`), and empirically verified against this repo's actual `User` model: `Model#save(options)` calls `await this.constructor.runHooks(\`before${hook}\`, this, options)`, and `Hooks#runHooks` invokes each hook via `hook.apply(this, hookArgs)` with that exact `options` object — no key whitelist or filtering is applied to create/save options (only finder methods like `findAll` warn on unrecognized keys, via a separate `warnOnInvalidOptions` path that `create`/`save` never call). This means a caller can set an arbitrary custom key on the options object passed to `User.create(values, options)`, and `beforeCreate` can trust that key completely, because it can only be set by code with access to the create/save call site — never by data flowing through `passwordHash`.

    Change the hook signature to `async beforeCreate(user, options)` and its body to exactly: `if (user.passwordHash && !(options && options.passwordAlreadyHashed)) { user.passwordHash = await bcrypt.hash(user.passwordHash, 12); }`. The invited path is unaffected: it calls `models.User.create` with no such option, so `options.passwordAlreadyHashed` is `undefined`, `!(options && options.passwordAlreadyHashed)` is `true`, and hashing proceeds exactly as today. This fix does not use `{ hooks: false }` on the create call — that would also disable `beforeValidate` (the email-normalisation hook), forking the tokenless path's normalisation behaviour away from the invited path's, which REG-07 forbids.
