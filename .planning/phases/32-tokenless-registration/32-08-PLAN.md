<objective>
Close BLOCKER 2 (CR-03) from 32-VERIFICATION.md / 32-REVIEW.md: Plan 32-05 wrapped
`models.User.create` in a try/catch so a create-time failure (duplicate-insert race, an
over-length value, a missing-column error) returns the identical uniform success message
instead of leaking raw ORM/DB error text. But `models.User.findOne` (the existing-user lookup)
and `createVerificationToken()` (the free-path-only token mint) both run BEFORE that try block --
a `findOne` rejection (connection-pool exhaustion, a transient DB error, a
`SequelizeDatabaseError` on an unmigrated target) still propagates raw Sequelize text --
including `.sql`, which mysql2 inlines bound parameter values into -- to an anonymous caller,
and it also skips `finishTokenlessRegistration` entirely, making that outcome both differently
shaped AND measurably faster than every other one. A `createVerificationToken` throw is a
free-path-only divergence of the exact class the 32-05 fix exists to eliminate, just one
statement earlier than the code it touched.

This plan widens the guarded region to cover the whole post-validation body (bcrypt.hash,
findOne, and createVerificationToken alongside the pre-existing create), so every tokenless
outcome -- including these two previously-unguarded failure modes -- exits through the single
`finishTokenlessRegistration` path. It also repairs two test-integrity findings from
32-REVIEW.md that this same code region's test file already contains (the WR-01 timing test
pins `Date.now` to a constant, making its central assertion unfalsifiable; the CR-01 equivalence
assertion still passes with the name-validation guard deleted), adds a startup-time check so an
unmigrated deployment target fails at boot instead of silently dropping every registration
forever, and corrects REQUIREMENTS.md's premature SEC-01 checkbox.

Depends on Plan 32-07 (both touch `user.resolver.js`; 32-07 edits `verifyEmail`/`updateUser`,
this plan edits `register` -- disjoint functions, sequenced only to avoid a file-overlap merge
conflict).
