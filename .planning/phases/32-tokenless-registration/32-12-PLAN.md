<objective>
Close 32-VERIFICATION.md's Gap 2 (Truth 7, broader manifestation / 32-REVIEW.md CR-03 second-round numbering): Plan 32-10 correctly closed the TOCTOU concurrency window in `updateUser`'s last-administrator guards by wrapping them in a locking transaction, but the counting query itself was never fixed -- both `updateUser`'s `otherVerifiedAdminCount` (now to be renamed) and `verifyEmail`'s admin-slot count filter on `role = 'ADMIN' AND emailVerified = true`, omitting `status`, while `isFunctioningAdmin` (`utils/auth.js:62-64`) -- the codebase's own single named definition of a usable administrator -- additionally requires `status === 'Active'`. This fails DETERMINISTICALLY in plain sequential use, no race required: promoting a Pending, verified self-registrant to ADMIN and then demoting the sole real admin lets the guard's own query see the Pending ADMIN as "1 other admin" and permits the demotion, driving functioning admins to zero -- and the identical omission in the bootstrap's admin-slot count then permanently blocks the ADMIN_EMAIL recovery path too, because it also sees the stranded Pending admin and never reaches `adminCount === 0`.

Purpose: apply Plan 32-11's opening lesson -- "check each guard's predicate before its locking" -- retroactively to the guard Plan 32-10 already locked, so the counting query matches `isFunctioningAdmin`'s definition exactly, and correct the comments that falsely claimed this was already true.

Output: both raw SQL admin counts require `status = 'Active'`; `updateUser`'s counting helper is renamed `otherFunctioningAdminCount` to match what it now actually counts; `utils/auth.js`'s stale line-number comment is replaced with symbol references; two sequential (non-concurrent) regression tests in `updateUser.test.js` and one in `verifyEmail.test.js` prove the fix.
</objective>
