<objective>
Wire up the "runs everywhere" layer on top of the full-stack test suite built in Phases 1-5: a single root `npm test` command (SETUP-03) and a greenfield GitHub Actions CI workflow (CI-01, CI-02, CI-03 mechanism, plus the D-07 documentation half of CI-03) that reproduces that exact command against a MySQL 8.4 service container matching the committed `env/test.env`.

Purpose: today there is no root-level test command and no `.github/workflows/` directory at all -- every workspace suite built in Phases 1-5 only runs if a developer remembers to run it manually, and nothing stops a broken commit from merging. This plan makes "run everything" one command and makes CI failures visible on every push/PR.
Output: root `package.json` `test` script, `.github/workflows/ci.yml`, and a new `## Continuous Integration` section in `README.md`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| GitHub `pull_request` event -> CI runner | A `pull_request` trigger (D-06, no branch filter) checks out and executes repo code -- including code from forks -- inside the ephemeral `ubuntu-latest` job. |
| `.github/workflows/ci.yml` -> third-party GitHub Actions | The workflow pulls `actions/checkout` and `actions/setup-node` from the GitHub Marketplace at pinned tags. |
| Committed test credentials (`env/test.env`) -> `services.mysql.env` in `ci.yml` | Non-production DB credentials are duplicated verbatim from a committed file into another committed file. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-06-01 | Tampering | `.github/workflows/ci.yml` action references | mitigate | Pin `actions/checkout@v7` and `actions/setup-node@v6` to specific, live-verified major-version tags (not `@main`/`@latest`); versions confirmed via `api.github.com` release endpoints in 06-RESEARCH.md, not training-data recall. |
| T-06-02 | Information Disclosure | `services.mysql.env` block in `ci.yml` | accept | Values reused are the already-committed, non-production `env/test.env` credentials (`portofolio`/`portofolio`, a throwaway dev JWT secret elsewhere in the same file) plus an arbitrary `MYSQL_ROOT_PASSWORD` never consumed by the app (D-04). Nothing new or production-sensitive is introduced by this plan. |
| T-06-03 | Elevation of Privilege | `pull_request` trigger running fork-PR code inside the job | accept | The workflow uses `pull_request` (not `pull_request_target`), so default `GITHUB_TOKEN` permissions on fork PRs are read-only and scoped to the triggering repo; the workflow declares and uses no secrets at all, so a fork PR gains no exploitable credentials merely by running the test suite. |
| T-06-04 | Denial of Service | Unbounded workflow runs (D-06: every push/PR, no branch filter) consuming Actions minutes | accept | Solo portfolio repo with a small, fast test suite (~7s combined per local run, confirmed above); acceptable cost for full push/PR coverage at this scale -- no rate limiting or path filtering added. |
| T-06-SC | Tampering | npm/pip/cargo installs | N/A | This phase introduces zero new npm/pip/cargo dependencies. `npm ci` in the workflow installs the already-committed, already-audited root `package-lock.json` from Phases 1-5 unchanged. 06-RESEARCH.md's "Package Legitimacy Audit" section confirms "Not applicable" -- no install tasks exist in this plan. |

No HIGH-severity threats identified without a mitigation. This plan adds only configuration/orchestration files (a root npm script, a CI workflow YAML, a README section) -- no new runtime code paths, no new inputs, no new secrets.
</threat_model>
