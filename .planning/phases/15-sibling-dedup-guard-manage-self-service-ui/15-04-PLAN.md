<objective>
Build `AdminMemberTable` — the searchable, client-side-paginated table over the whole
`familyMembers` list that is the admin's entry point into D-03's "table → focus one member into
the grouped panel" flow. This is genuinely new MUI composition (no `Table`/`TablePagination`
precedent exists yet in this codebase — every other list uses an unpaginated `Stack` of rows), but
is otherwise a data-in/callback-out presentational component with no GraphQL fetch of its own.

Purpose: MNG-03 requires an admin to manage "the whole tree ... hundreds of nodes" from `/manage`;
per 15-RESEARCH.md's Open Question 2, client-side `TablePagination` over the full, already-shipped
`familyMembers` query result is sufficient at this scale with zero backend change.
Output: `AdminMemberTable.jsx` and its colocated RTL test.
</objective>

<interfaces>
Prop contract (a later wiring plan depends on this exact shape):
```
AdminMemberTable({ members, onSelect })
```
- `members`: flat array already fetched by the caller via the existing `familyMembers` query
  (`requireAdmin`-gated, unchanged this phase), shaped
  `{ id, firstname, lastname, fullname, gender, linkedUser: { id, name, email } | null }`. This
  component does NOT fetch — it is purely presentational over the array it's given (the same
  "server is the only source of truth, client never re-derives" rule that governs every other
  `/manage` component this phase).
- `onSelect(member)`: fired when a row is clicked, with that row's full object.
</interfaces>
