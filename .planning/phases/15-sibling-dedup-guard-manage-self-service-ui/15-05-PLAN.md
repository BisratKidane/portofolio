<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser route request → `/manage` | The client-side `ProtectedRoute` redirect is UX-only; every query/mutation `ManagePage` calls is independently guarded server-side (`requireFamilyAccess`, unchanged) |
| `ManagePage`'s `onEdit` wiring → `editMember` mutation | A client-side wiring bug (e.g. allowing `onEdit` on an out-of-scope member) cannot produce a successful out-of-scope write — the resolver's own `computeEditableScope`/lock check is the actual enforcement |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-09 | Spoofing / Elevation of Privilege | Unlinked user navigating directly to `/manage` | mitigate | Reuses the existing, already-proven `ProtectedRoute` (D-12) with no `allowedRoles` override, identical to `dashboard`'s gate; verified by a new route-level test exercising the real `/manage` path (not just `ProtectedRoute` in isolation). Real enforcement is server-side `requireFamilyAccess` on every query/mutation this page calls (unchanged this phase). |
| T-15-10 | Elevation of Privilege | `ManagePage`'s `onEdit`/`onAddRelative` wiring | mitigate | A client-side wiring defect here can at most attempt a mutation the server rejects — `editMember`'s and `addParent`/`addSpouse`/`addChild`/`addSibling`'s own `computeEditableScope` checks (Phase 14, unchanged) are the actual boundary. Residual risk accepted: a bug here degrades to a rejected mutation + error Alert, not a successful out-of-scope write. |
| T-15-11 | Tampering (stale-capability route) | `/admin/link-members`'s retirement | mitigate | The route now unconditionally redirects to `/manage` for every visitor rather than rendering any residual admin-linking UI — verified by the rewritten `AdminLinkMembers.test.jsx`. |

</threat_model>
