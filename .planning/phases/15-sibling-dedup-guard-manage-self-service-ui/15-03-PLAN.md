<interfaces>
Prop contract (a later wiring plan depends on this exact shape — no changes without updating both):
```
AddRelativeDialog({ open, relationType, targetId, inScopeMembers, onClose, onCreated })
```
- `relationType`: one of `'parent' | 'spouse' | 'child' | 'sibling'` — the SAME lowercase strings
  `RelationshipGroupedPanel`'s `onAddRelative` callback emits (built in a separate, parallel plan).
- `targetId`: the `id` of the FamilyMember this add-relative action is being performed on behalf of
  (maps to every mutation's `memberId` argument).
- `inScopeMembers`: array of `{ id, fullname }` — the caller's already-filtered, in-scope member list
  (Phase 14 D-02); used ONLY for the `child` relation type's optional "other parent" Autocomplete.
  NEVER fetch or filter members inside this component — the caller owns scope-filtering.

Exact mutation SDL to send (from `backend/src/schemas/familyMember.schema.js`, verified against
`15-RESEARCH.md`'s "Every mutation the /manage UI must send"):
```graphql
mutation AddParent($memberId: ID!, $role: ParentRole!, $newMember: NewFamilyMemberInput!) {
  addParent(memberId: $memberId, role: $role, newMember: $newMember) { id fullname }
}
mutation AddSpouse($memberId: ID!, $newMember: NewFamilyMemberInput!) {
  addSpouse(memberId: $memberId, newMember: $newMember) { id fullname }
}
mutation AddChild($memberId: ID!, $role: ParentRole!, $newMember: NewFamilyMemberInput!, $otherParentId: ID) {
  addChild(memberId: $memberId, role: $role, newMember: $newMember, otherParentId: $otherParentId) { id fullname }
}
mutation AddSibling($memberId: ID!, $newMember: NewFamilyMemberInput!) {
  addSibling(memberId: $memberId, newMember: $newMember) { id fullname }
}
```
`NewFamilyMemberInput` fields (identical to `AdminLinkMembers.jsx`'s `EMPTY_FORM`):
`firstname` (required), `lastname` (required), `gender` (required enum `Male|Female|Other`),
`mothersname`, `email`, `birthdate`, `deathdate`, `phone`, `address` (all optional).
</interfaces>

| Boundary | Description |
|----------|--------------|
| `inScopeMembers` prop (caller-supplied) → the child relation type's Autocomplete `options` | This component must never widen the picker beyond what its caller supplies — it has no fetch of its own to accidentally broaden |
| Browser form submission → `addParent`/`addSpouse`/`addChild`/`addSibling` GraphQL mutations | The actual scope/permission/REL-06 enforcement happens server-side in the resolver/service layer, unchanged by this plan |
