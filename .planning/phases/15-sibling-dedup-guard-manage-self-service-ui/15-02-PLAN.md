<interfaces>
`MemberCard` prop contract (both later plans depend on this exact shape):
```
MemberCard({ member, isAdmin, actingUserId, isSelf, isDerived, onEdit, onRewire, onDelete })
```
- `member`: a FamilyMember-shaped object — `{ id, fullname, gender, linkedUser: { id } | null, ... }`
- `actingUserId`: the acting USER's own `id` (from `useAuth().user.id` — a `User` row id, NOT a
  `FamilyMember` id). The D-06 lock compares `member.linkedUser.id !== actingUserId`, mirroring
  `familyMember.resolver.js`'s `editMember` check EXACTLY (`target.linkedUser.id !== user.id`) —
  passing a `familyMemberId` here instead of the acting `User.id` would silently mis-render the lock.
- `isSelf`: true when `member.id === self.id` — always editable regardless of `linkedUser` (D-06:
  "can always edit their own record").
- `isDerived`: true only for Siblings-section rows (D-02).
- No `onRewire` mutation exists in the Phase 14 GraphQL surface this phase consumes (no
  addParent/spouse "rewire an existing edge" mutation was shipped, and this phase adds no new
  backend mutations per 15-CONTEXT.md's domain boundary). `onRewire` is accepted as a prop for
  forward-compatibility but MUST NOT be called by any button this task renders — do not fabricate a
  "Rewire" button with no backing capability. This is a known, documented gap (see 15-CONTEXT.md
  D-03/D-07's "rewire" mention) — flagged to the phase's PLANNING COMPLETE summary, not silently
  built as dead UI.

`RelationshipGroupedPanel` prop contract:
```
RelationshipGroupedPanel({ scope, isAdmin, actingUserId, onAddRelative, onEdit, onDelete })
```
- `scope`: `{ self, parents: FamilyMember[], spouses: FamilyMember[], children: FamilyMember[], siblings: FamilyMember[] }`
  — the exact shape `computeEditableScope`/grouped `myEditableMembers` data already provides.
- `onAddRelative(relationType)`: called with one of the four lowercase strings
  `'parent' | 'spouse' | 'child' | 'sibling'` — this exact casing is the shared contract
  `AddRelativeDialog` (built in a separate, parallel plan) also uses; do not change it without
  updating both.
</interfaces>
