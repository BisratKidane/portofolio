<objective>
Close the one open gap from `31-VERIFICATION.md` (Roadmap SC-3 / INVITE-03): `verifyEmail`'s
auto-activation currently promotes a Pending registrant to Active based solely on the EXISTENCE
of an `Invitation` row keyed by `registeredUserId`. It never checks whether the inviter named on
that row is *currently* an ADMIN in good standing, so two confirmed-exploitable paths bypass
approval: (1) pre-Phase-31 invitations issued by a linked, Active, non-admin family member under
the old `requireFamilyAccess` guard (still live -- no migration touches them), and (2) an invitation
whose inviter is later demoted to USER, disabled, or rejected before the invitee verifies.

This plan closes both paths with a single runtime fix: re-check the vouching admin's CURRENT
role and status inside `verifyAndPromote`'s existing transaction, immediately before promoting.
Per the migration-guidance decision required by this gap-closure run: **no migration is added.**
A `020-*.sql` sweep would only close path (1) (existing rows) and would do nothing for path (2)
(an admin demoted *after* the migration runs). The runtime re-check subsumes both -- it re-reads
the inviter's live row on every redemption, so a legacy non-admin-issued row and a freshly-demoted
admin's row fail the exact same check, forever, with no expiry window to maintain. Stated as a
choice: of the two candidate closures for the verifier's legacy-window item -- (a) a `020-*.sql`
migration that expires pre-Phase-31 non-admin-issued Pending rows, or (b) a runtime re-check at
redemption -- this plan takes (b), because (b) fully subsumes (a) while (a) cannot cover path (2)
at all. This is this plan's own reasoning, not a directive carried over from `31-VERIFICATION.md`,
whose `missing:` list names the outcome ("a migration or lazy sweep that closes the existing
window") without prescribing which.

**Explicit deviation note (D-05 caveat):** `31-CONTEXT.md`'s
D-05 declined a migration and an account-side provenance column as a *scoping* decision for the
original phase -- it never considered or accepted the non-admin-inviter exploit this plan closes.
This plan does not violate D-05: it still adds no migration and no provenance column. It adds a
runtime read of `Invitation.inviterId`'s CURRENT row, which is a strictly tighter interpretation
of D-05's own "keyed on the FK alone" premise -- the FK was always meant to identify the vouching
admin; this plan is the first place that admin is actually verified rather than assumed.

Test-first ordering (per the user's red-green-refactor workflow, mandatory for this security fix):
Task 1 writes the 3 negative/regression tests FIRST and confirms 2 of them go RED against the
current (unfixed) code. Task 2 implements the fix, confirms all 3 go GREEN, then performs a
mandatory mutation-test-the-guard step -- neutering the new check must turn the 2 inviter-vouching
tests back RED, proving they have real teeth (this codebase has a documented history, Phases 14,
15, 30, and now 31 itself, of authorization guards surviving a green suite).

Purpose: make INVITE-03's actual premise -- "an invited person, vouched for by the admin who
invited them, activates on email verification alone" -- true in code, not just true for the
happy-path population the original phase's tests exercised.
Output: `verifyAndPromote` in `backend/src/resolvers/user.resolver.js` re-verifies the inviter at
redemption time; `verifyEmail.test.js` gains 3 new tests (12 total non-skipped assertions of
correct behavior, up from 9); the mutation-test-the-guard step is run and its RED/GREEN result
recorded in this plan's SUMMARY.
