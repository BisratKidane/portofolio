<objective>
Make `verifyEmail` promote an invited registrant straight to `Active` inside its existing transaction (D-04, D-05, D-06, D-07), and clean up `register`'s invited-path side effects that no longer make sense once approval is skipped (D-11, D-13).

Purpose: this is INVITE-03 — "a person who registers through an admin invitation and verifies their email becomes Active automatically." The admin already vouched for them at invite time; email verification is the only remaining gate. F-03 makes this security-relevant, not just a data update: the resolver's own return statement reads the account back out after the transaction, so the promotion must be committed before that read or the response lies about the account's own state.
Output: `backend/src/resolvers/user.resolver.js` with the promotion inserted into `verifyEmail` and `register`'s notify-call/message updated; `verifyEmail.test.js` and `register.test.js` extended to pin all of it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client GraphQL request → user.resolver.js (`register`, `verifyEmail`) | Untrusted, unauthenticated: both mutations accept a client-supplied token with no prior auth context. `verifyEmail`'s token is the sole authority for which account gets acted on. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-31-05 | Elevation of Privilege | `verifyEmail` promotion | mitigate | D-06's atomic conditional `WHERE id = user.id AND status = 'Pending'` update means a `Rejected` or `Disabled` account cannot be resurrected by re-submitting (or replaying) a verification token — the update simply affects zero rows. Pinned by two dedicated tests (Rejected, Disabled). |
| T-31-06 | Tampering (of the response, not the DB) | `verifyEmail`'s return statement | mitigate | F-03: the promotion runs and commits inside the same transaction as token consumption, strictly before the outer `await user.reload()` and the `return { token, user }` line — so the token and user object handed back to the client always describe the post-commit state, never a stale `Pending` snapshot. Pinned by asserting `response.data.verifyEmail.user.status` directly on the mutation response, not a follow-up query. |
| T-31-07 | Repudiation | Auto-activation with no audit trail | mitigate | A fire-and-forget `invitation.activated` audit row (actorUserId/invitationId/targetUserId) is written after the transaction commits, so "why did this account become Active with no approveUser call" remains answerable from the append-only log, consistent with `user.approved`/`user.rejected` from Phase 30. |
| T-31-08 | Information Disclosure (absence of, not presence of) | Dropped `notifyAdminsOfPendingRegistration` call in `register` | accept | D-11 is a deliberate scope reduction, not an oversight — the invited path has nothing for an admin to review, so there is nothing to notify them of. The "your invitee joined" notice was considered and explicitly deferred in CONTEXT.md; no admin loses the ability to see the account (it just never enters the approval queue, per D-09 in Plan 31-01). |

No package installs occur in this plan (no `T-31-SC` row needed).
