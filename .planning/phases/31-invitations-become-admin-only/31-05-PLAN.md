<objective>
Close the two residual gaps from `31-VERIFICATION.md`'s re-verification of plan 31-04 (both independently confirmed by the verifier from the code, and both raised as CR-01/CR-02 in the fresh `31-REVIEW.md` run after 31-04 landed):

**Gap 1 (T-31-12, TOCTOU not structurally closed):** `verifyAndPromote`'s inviter re-check (`models.User.findByPk(invitation.inviterId, { transaction: t })`, `user.resolver.js:287`) is a plain, non-locking read. It is safe today only as an accidental side effect of `users.role` having no index, which forces the unrelated admin-slot `SELECT COUNT(*) ... FOR UPDATE` two statements earlier to full-table-scan-lock every row in `users`, incidentally including the inviter's. The comment directly above the check (`user.resolver.js:280-286`) and 31-04's own threat model both claim re-reading the row closes the TOCTOU; it does not, on its own. Adding the obvious `KEY idx_users_role (role)` optimization to that `COUNT(*)` query would silently reopen the window with zero test failures, because no existing test exercises a genuinely concurrent modification of the inviter row during redemption.

**Gap 2 (CR-02, `vouchedByAdmin` omits `emailVerified`):** `vouchedByAdmin` (`user.resolver.js:288`) is `Boolean(inviter) && inviter.role === 'ADMIN' && inviter.status === 'Active'` — it does not require `inviter.emailVerified === true`, unlike the admin-slot count two lines above it (`role = 'ADMIN' AND emailVerified = true`), `updateUser`'s last-administrator guard (`role: 'ADMIN', emailVerified: true`), and `getUserFromRequest` (which treats any unverified account, including an ADMIN, as not logged in at all). An admin who changes their own or another admin's email address has `emailVerified` reset to `false` while `role`/`status` stay `ADMIN`/`Active` — that account cannot authenticate at all, yet every invitation it previously sent still silently auto-activates its registrant.

**Fix for both:** (1) add `lock: t.LOCK.UPDATE` to the inviter `findByPk` call so the read is a genuine InnoDB locking read (bypasses the transaction's REPEATABLE READ snapshot, always sees the latest committed row) rather than relying on the incidental full-table lock; (2) extract the three-part "currently-functioning administrator" predicate (role, status, emailVerified) into a single named helper, `isFunctioningAdmin(user)`, in `backend/src/utils/auth.js`, scoped to an already-loaded `User` instance, and use it for `vouchedByAdmin`. This is a deliberate, narrow extraction — it does NOT touch the admin-slot raw SQL `COUNT(*)` (`user.resolver.js:263-264`, a raw SQL string, not a JS predicate over a loaded instance) or `updateUser`'s last-administrator guard (`user.resolver.js:425-427`, a Sequelize `where`-clause count over a *different* set of users, not an in-memory check on one loaded row). Unifying those two would change their query/locking shape and risks silently altering the last-administrator floor or the admin-slot count's semantics, which is out of scope for this gap-closure plan. `isFunctioningAdmin` gives the one call site that genuinely is an in-memory instance check (`vouchedByAdmin`) a documented, reusable name, and is available for any future in-memory-instance call site without inventing a fourth hand-rolled variant.

Both fixes are read/lock-only changes to `verifyAndPromote`'s existing transaction — D-04, D-05, D-06, D-07, D-08, and F-03 (all preserved by 31-04) are untouched by this plan.

Test-first ordering (per the user's red-green-refactor workflow, mandatory for security fixes, matching 31-04's own structure): Task 1 writes the two new negative tests FIRST and confirms both go RED against the current (unfixed) code. Task 2 implements both fixes, confirms GREEN, then performs two separate mandatory mutation-test-the-guard steps (one per gap) — this codebase has a documented history (Phases 14, 15, 30, and 31 itself, twice now) of authorization guards surviving a fully green suite while resting on an undocumented assumption.

Purpose: make `verifyAndPromote`'s "vouched for by the admin who invited them" check (INVITE-03) structurally correct — safe against a concurrent demotion, and consistent with this codebase's own established definition of a functioning administrator — rather than correct only by the accident of a missing index and a narrower predicate than the rest of the codebase uses.
Output: `verifyAndPromote` in `backend/src/resolvers/user.resolver.js` locks the inviter row and gates on `isFunctioningAdmin`; `backend/src/utils/auth.js` gains the new exported `isFunctioningAdmin` helper (plus unit coverage in `auth.test.js`); `verifyEmail.test.js` gains 2 new regression tests (15 total non-skipped assertions of correct behavior, up from 13); both mutation-test-the-guard results are recorded in this plan's SUMMARY.
