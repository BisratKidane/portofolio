<objective>
Give the `User` account somewhere to record its own approval/rejection decision: add `approvedAt`, `approvedBy`, `rejectedAt`, `rejectionReason` to the `User` Sequelize model (D-04), write the portable manual migration `019-add-users-approval-columns.sql` for already-provisioned databases, prove that migration's DDL is valid on a real local MariaDB engine via a self-contained scratch-database dry run, and then have a human apply it to the actual local dev database as an explicit, non-silent step (F-03).

Purpose: A self-registrant arriving in Phase 32 has no invitation row, so `approveUser`/`rejectUser` (Plan 30-02) need the account itself to carry the same four decision facts `invitations` already stores. The backend test DB self-provisions from these model definitions via `sequelize.sync({ force: true })` (`backend/test/globalSetup.js:11`), so this plan alone is what makes the automated suite in Plan 30-03 exercise these columns — the manual SQL file is only needed for databases that already exist (local dev, prod), which `sync()` never alters.
Output: `User.js` with four new nullable fields; `019-add-users-approval-columns.sql` committed and proven to apply cleanly on local MariaDB via an isolated scratch DB; a human confirmation that the same SQL has been applied to the real local dev database.
</objective>
