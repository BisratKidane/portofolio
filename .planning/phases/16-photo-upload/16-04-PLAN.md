<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → upload route | Multipart body, `Content-Type` header, and filename are all untrusted input |
| Member-user → another member's record | Editable scope is the write-authorization boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-08 | Tampering | Path traversal via multipart filename | mitigate | `req.file.originalname` never read past multer's callback; filename is exclusively `generatePhotoFilename(detected.ext)` |
| T-16-09 | Tampering | Content-type/extension spoofing (malicious payload disguised as an image) | mitigate | `fileTypeFromBuffer` is the sole authority; reject on `undefined` or mismatch regardless of the declared header/extension |
| T-16-10 | Denial of Service | Oversized upload / memory exhaustion | mitigate | `multer`'s `limits.fileSize` (5 MB) enforced at the parser level, before the full body is buffered; dedicated `multerErrorHandler` returns a clean 400, not a 500 |
| T-16-11 | Elevation of Privilege | Uploading a photo for a member outside the actor's editable scope | mitigate | Reuses `computeEditableScope`/`requireFamilyAccess` exactly as every Phase 14 mutation — no new authz logic invented |
| T-16-12 | Repudiation | Replace/remove orphaning the previous file | mitigate | `finalizePhotoReplacement` (16-02) sequences write-new → DB commit → delete-old, discarding the new file on commit failure |
</threat_model>
