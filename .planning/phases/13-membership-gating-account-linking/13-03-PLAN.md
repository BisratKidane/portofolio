<objective>
Enforce the membership gate in the SPA: any authenticated, non-admin user with no linked member is routed to a static `/pending` screen (D-01/D-02), while a linked user or any ADMIN reaches the app normally (ACC-03 carve-out reflected in the frontend) — immediately after login or email verification, not only after a page refresh.

Purpose: this is the frontend half of ACC-01 — the backend `requireFamilyAccess` guard from Plan 13-02 is the authoritative enforcement, but the SPA must not dead-end or error-loop an unlinked user, and it must not incorrectly bounce a *linked* user to `/pending` either. `authenticate()` in `AuthContext.jsx` sets `user` directly from the `login`/`verifyEmail` mutation payload and never re-runs the `me` query, and `Login.jsx`/`VerifyEmail.jsx` navigate client-side without a page reload — so `familyMemberId` must be present on all three operations' `user`/`me` selection sets, not only `ME_QUERY`, or a linked user is misrouted to `/pending` until a manual refresh.
Output: `frontend/src/pages/Pending.jsx` (new); extended `ProtectedRoute.jsx` (pending-gate branch); extended `AuthContext.jsx` (`familyMemberId` added to the `me`, `login`, and `verifyEmail` operations); `/pending` route in `App.jsx`.
</objective>

export default function ProtectedRoute({ allowedRoles }) {
  const { loading, user } = useAuth();
  if (loading) { return <Box>...<CircularProgress /></Box>; }
  if (!user) return <Navigate to="/login" replace />;
  if (allowedRoles && !allowedRoles.includes(user.role)) return <Navigate to="/dashboard" replace />;

}

const ME_QUERY = `

    me { id name email role }
  }
