<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Any JWT-authenticated caller → `familyMember`/`familyMembers` resolvers | `requireFamilyAccess`/`requireAdmin` are the sole gate |
| ADMIN caller → `linkUserToMember` mutation | Fully-trusted role acting on arbitrary user/member ids, admin-global by design (D-06) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-13-04 | Elevation of Privilege | `linkUserToMember` mutation | mitigate | `requireAdmin(user)` is the first statement in the resolver body — thrown-guard convention, tested by the "rejects a non-admin caller" case. |
| T-13-05 | Information Disclosure / IDOR | `linkUserToMember(userId, memberId)` | accept | The mutation accepts arbitrary user/member ids with no ownership scoping — by design: linking accounts to members is an admin-global action across the whole tree (D-06/ACC-02), not a self-service action, and the caller is already a fully-trusted ADMIN role, so enumerating other users'/members' ids is not a privilege-boundary violation at this trust level. |
| T-13-06 | Tampering (race condition) | `linkUserToMember` vs. the `users_familyMemberId_unique` DB constraint | mitigate | Two concurrent `linkUserToMember` calls targeting the same `memberId` race at the DB layer; the resolver catches `UniqueConstraintError` and returns a friendly rejection instead of a partial/inconsistent write or a leaked SQL error. |
| T-13-07 (phase-core) | Elevation of Privilege | `familyMember` query | mitigate | The LOCKED adversarial test (Task 1) proves a verified-but-unlinked, non-admin JWT calling `familyMember` directly — bypassing the SPA entirely — is rejected server-side (SC5). |

</threat_model>
