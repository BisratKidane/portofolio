|----------|--------------|
| Search-box typed text → client-side filterOptions | The picker's typed query is client-side-only, matching an already-fetched, already-authorized in-memory `inScopeMembers` array via `createFilterOptions`'s internal string matching — no server round-trip, no query construction from user input, no new network surface. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-04 | Denial of Service (ReDoS via typed search input) | `AddRelativeDialog.jsx` `filterOptions` | accept | `createFilterOptions`'s internal matcher (MUI, not custom regex) and the `stringify` callback here use plain string concatenation and comparison, not a user-constructed `RegExp` — no regex-compilation step, therefore no ReDoS surface regardless of typed input length. |
| T-23-05 | Information Disclosure (surfacing out-of-scope members) | `AddRelativeDialog.jsx` `filterOptions` | accept | `filterOptions` only ever filters within the `options={inScopeMembers}` array already passed into the component — it narrows visible matches, it cannot surface any member not already present in that already-authorized, already-scoped prop. No change to which members are fetched or authorized (Phase 14 scoping, unchanged). |

No new endpoints, no new mutations, no new auth/session logic, no new external dependency (createFilterOptions ships with the already-installed @mui/material package).
