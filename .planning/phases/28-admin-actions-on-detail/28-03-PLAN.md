<objective>
Close the cache-invalidation gap Phase 27 deliberately deferred: add a
`refreshEntry(id)` method to `useDescendantNav` that evicts and refetches a
single cached descendant (or the current top/head) with one bounded GraphQL
request, and a matching `REFRESH` action to the pure `navReducer` so the ref
write actually triggers a re-render. This is the foundation Plans 28-04
(edit-in-place) and 28-05 (add-in-place + auto-expand) both consume.

Purpose: `useDescendantNav`'s cache is a ref (PERF-03 requirement — a write
alone never re-renders). Every existing fetch path (`ensureEntry`) is a
cache-hit-or-fresh-fetch; none of them can force a refetch of an id already
in cache. D-04 requires exactly that capability.

**Revision note (plan-checker blocker):** `refreshEntry` must be provably
id-agnostic — it is the ONLY refresh mechanism Plan 28-04 uses, for every
render site including the head. `nav.topPerson` resolves from
`cache.current.get(state.topId)?.self ?? mainPerson`; once a cache entry
exists for `state.topId` (which happens on first render via the
`mainPerson?.id`-keyed effect), the `mainPerson` fallback is dead code from
that point on — only a write to `cache.current.get(state.topId)` can ever
change what actually renders as the head. `refreshEntry(id)` already does
exactly that write for whatever `id` it's called with; this plan adds an
explicit test proving it works for `state.topId` too, not just nested
descendants, so this exact class of bug is caught here rather than
downstream in Plan 28-04.

Output: `useDescendantNav.js` (+ test), `descendantNav.reducer.js` (+ test)
</objective>

<!-- Current useDescendantNav contract — do not rename existing exports/fields. -->

useDescendantNav(mainPerson) returns:
  { topPerson, topExpanded, gen1, expandedChildId, gen2, loadingId,
    onExpandTop, onExpandChild, onExpandGrandchild }

topPerson = cache.current.get(state.topId)?.self ?? mainPerson  (useDescendantNav.js:84)
gen1 = cache.current.get(state.topId)?.children ?? []            (useDescendantNav.js:85)
gen2 = ... cache.current.get(state.expandedChildId)?.children ... (useDescendantNav.js:86)

The `mainPerson` fallback in `topPerson` only applies BEFORE any cache entry
exists for `state.topId` (i.e. the very first render of a given id). The
mount-time `useEffect` (keyed on `mainPerson?.id` only, useDescendantNav.js:43-48)
seeds `cache.current.set(mainPerson.id, { self: mainPerson, children: existing?.children })`
exactly once per id-change — so after that, `topPerson` ALWAYS resolves from
`cache.current.get(state.topId)?.self`, never from a re-assigned `mainPerson`
prop with the same id. This is WHY a refresh mechanism that only updates the
`mainPerson` React state (without touching `cache.current`) can never change
what's rendered as the head.

cache: useRef(new Map()) — entry shape { self, children }, `children` stays
  `undefined` until a fetch resolves (cache miss signal).
ensureEntry(person): cache-hit -> Promise.resolve(); cache-miss -> fetches
  EXPAND_CHILDREN_QUERY(id: person.id) which returns ONLY `children` (not the
  target's own fields) -- this is why the new REFRESH_PERSON_QUERY below must
  fetch the target's OWN fields too (an edit/add-spouse changes those).

New contract this plan adds (do not deviate — Plans 28-04/28-05 depend on
these exact names):
  refreshEntry(id) -> Promise<familyMember-shaped object | null>
    - Always issues a fresh request (never a cache-hit short-circuit, unlike ensureEntry)
    - Works identically for ANY id — a gen1/gen2 descendant, the current
      state.topId (whether that's the original head or a forward-shifted
      promoted top), or an id not yet in cache at all. No special-casing by
      "is this the head" is needed or should be added, in useDescendantNav OR
      in any caller (Plan 28-04's refreshAfterMutation calls this
      unconditionally for every target).
    - On resolve: cache.current.set(id, { self: <own fields minus children>, children: <fresh children array> })
    - Dispatches { type: 'REFRESH' } to force a re-render
    - Sets/clears loadingId the same way ensureEntry does
  navReducer(state, { type: 'REFRESH' }) -> { ...state } (new reference, same
    field values — the minimal "bump" needed since state didn't logically
    change but the ref cache backing it did)
