<objective>
Wire DetailPage's three no-op `onEdit={() => {}}` stubs to the real, unchanged
`EditMemberDialog`, closing the field-completeness gap (the `/detail` read
queries carry only card-display fields, not the editable set) by fetching a
full member record before the dialog opens, and refresh the edited card in
place on save — via Plan 28-03's `nav.refreshEntry`, uniformly, for every
render site including the head.

Purpose: this is PERM-01 (SC-1) — the edit button already exists and is
already gated (Phase 25); this plan makes it functional. It also defines
`refreshAfterMutation`, the shared refresh router that Plan 28-05's
add-relative wiring reuses unchanged.

**Revision note (plan-checker blocker, fixed here):** the original version of
this plan routed head refreshes through `loadPersonById(mainPerson.id)`,
following D-04's literal wording. That is broken by construction:
`DetailPage` renders `<PersonCard member={nav.topPerson} .../>`, and
`nav.topPerson` resolves from `cache.current.get(state.topId)?.self` — NOT
from the `mainPerson` React state variable — once a cache entry for
`state.topId` exists (which it always does after the first render;
`useDescendantNav`'s cache-seed effect is keyed only on `mainPerson?.id`, so
a same-id `setMainPerson(fresh)` from `loadPersonById` never re-runs it and
never touches the cache). `refreshAfterMutation` now calls
`nav.refreshEntry(member.id)` for EVERY target — head, gen1, gen2, or a
forward-shifted promoted top — which is the only mechanism that actually
writes `cache.current` and dispatches `REFRESH`. `loadPersonById` remains in
use ONLY for genuinely id-changing loads (initial head load, search-select),
never for refresh-after-mutation.

Output: `DetailPage.jsx` (+ test)
</objective>
