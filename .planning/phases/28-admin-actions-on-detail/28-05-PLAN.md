<objective>
Wire the Add-menu control (Plan 28-02) to the existing, unchanged
`AddRelativeDialog` at all three `/detail` render sites, and — on a
successful add — refresh the affected person in place (Plan 28-04's
`refreshAfterMutation`) and auto-expand them if their children were
previously collapsed, so a newly-added child is immediately visible without
an extra click (D-05).

Purpose: this is the remaining half of PERM-02/SC-2 — Plan 28-02 built the
visible control, Plan 28-04 built the refresh router; this plan connects
them to a real dialog and closes the loop end-to-end.

**Revision note (plan-checker blocker + WARNING 2, fixed upstream in Plan
28-04, verified here):** the plan-checker identified that add-spouse-to-head
and add-child-to-head (both when already-expanded and when
previously-expanded-then-collapsed) would silently stay stale, because the
ORIGINAL `refreshAfterMutation` routed the head through `loadPersonById`,
which never touched the per-id cache `nav.topPerson`/`gen1` actually render
from. Plan 28-04 now fixes `refreshAfterMutation` to route EVERY target
(head included) through `nav.refreshEntry` unconditionally — which means
`handleAddCreated`/`autoExpandIfCollapsed` in THIS plan need NO code change
to work correctly for the head: `refreshAfterMutation` already writes the
head's fresh `self` (including its updated `spouses` array) and fresh
`children` into the cache and dispatches `REFRESH` before
`autoExpandIfCollapsed` ever runs. This plan's job is to prove that with
explicit head-targeted test cases (WARNING 2) — see Task 1's new behavior
bullets below.
</objective>
